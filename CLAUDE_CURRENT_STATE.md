## 1. Что за проект

Эволюция уже работающей продакшн-SaaS АСКУЭ (`ASK/fetched/` → VPS `147.45.212.205`,
pm2-процесс `irz-web-gpio`, порт 3005, домен `askue.o-dir.ru`) в более крупную целевую
архитектуру (мультитенантность с ролями, партнёрская сеть, revenue-модель, AI-агенты) —
описана в `00_MASTER_PROMPT.md`…`04_ROADMAP.md` в корне репозитория. Работа ведётся в
**отдельном** от продакшн-деплоя git-репозитории `esforhouse-dot/ASKUEaudit` (создан
09.09.2026) — коммиты в этот репозиторий НЕ деплоятся на VPS автоматически, деплой отдельным
явным шагом с разрешения владельца.

**Три участника:** владелец (принимает решения, даёт PASS/разрешения) ↔ GPT в отдельном чате
(архитектурный ревьюер, формулирует задачи и проверяет отчёты) ↔ Claude Code здесь (исполняет
строго в рамках одной задачи за раз, отчитывается, коммитит, останавливается).

**Процесс:** Stage 2 (форензик-аудит, read-only) → Stage 2.5A (сведение аудита с целевой
архитектурой, решения владельца) → Stage 3 (план реализации по задачам-карточкам) →
пофазное исполнение (`Execute Task P0-XX`).

## 3. Все утверждённые решения (AUTHORITATIVE)

Полный текст — `RECONCILIATION/05_ARCHITECTURE_DECISIONS.md` (ADR-01…ADR-18). Коротко:

- Форма системы не меняется: Modular Monolith + Workers, SQLite остаётся, протокол
  Mercury/iRZ (`mercury*.js`) не трогается — KEEP AS IS (ADR-01/02/05).
- Нет ограничения «1 project = 1 modem» — целевая модель Organization → Objects → Modems →
  RS-485 → Meters, реализация в Phase 1 (ADR-14).
- Сущность `Organization` вводится, additive, физически — в Phase 4, не раньше (ADR-15).
- `modem_tariffs` — deprecated, история архивируется, не удаляется (ADR-16).
- **`irz-modem-control` (корневой легаси) — НЕ ТРОГАТЬ вообще, ни на одной фазе** (ADR-17).
- Financial Calculation Safety: старый float-путь → regression fixtures → новый Decimal-путь →
  подтверждённое совпадение на живом трафике → новый путь становится единственным → старый
  **удаляется** (не остаётся навсегда параллельно) (ADR-06/07). Ещё не начато — Phase 3.
- Секреты: вынесены из `CLAUDE.md` (сделано), сама ротация credentials — `DEFERRED/ACCEPTED
  OWNER RISK` (см. §9) (ADR-08).
- Deployment lifecycle — двухуровневый staging, Уровень 1 работает, Уровень 2 спроектирован,
  не запущен (ADR-09, см. `IMPLEMENTATION_PLAN/DEPLOYMENT_LIFECYCLE.md`).
- Backup/restore — механизм построен и проверен, деплой (cron, off-server хранилище) —
  `BLOCKED/OPEN OWNER DECISION` (ADR-10).
- Reliability investigation 140+ рестартов — завершено, причина установлена, follow-up фикс
  не нужен (ADR-11).
- `audit_logs` — построен и проверен, не задеплоен (ADR-12).
- **Правило конфликтов (ADR-18): если найден конфликт между AUTHORITATIVE-решением и фактами —
  не решать самостоятельно, фиксировать как `OPEN OWNER QUESTION` и останавливаться.**
- **Рабочее правило (не ADR, прямое указание владельца 2026-09-09): коммитить и пушить сразу
  после каждой задачи, не дожидаясь отдельного «PASS» — ревью идёт по запушенному состоянию.**
  Но каждая задача всё равно ждёт явного «Execute Task P0-XX»/«Переходи к P0-XX» перед началом.
- ADR-04 (permission-based RBAC) — **всё ещё PROPOSED, не AUTHORITATIVE** — нужно отдельное
  утверждение владельца перед детализацией Phase 4.
