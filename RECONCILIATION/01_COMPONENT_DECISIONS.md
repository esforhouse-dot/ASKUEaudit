## 2. Organizations / Multitenancy

| Компонент | Решение | Обоснование |
|---|---|---|
| `projects` + tenant-isolation middleware (`req.projectId`→`req.modem`→`req.meter`, строго через FK-scoped SQL) | **KEEP AS IS** | Паттерн корректен, живьём проверен на невозможность подмены `meterId` (`AUDIT/09`). Один из немногих компонентов без замечаний. |
| Ограничение «1 проект = 1 активный модем» (`server.js` middleware, `LIMIT 1`) | **EXTRACT + AUTHORITATIVE (owner, 2026-09-09)** — не архитектурное ограничение, снимается | Целевая модель: **Organization → Objects/Projects → Modems → RS-485 → Meters**, N модемов на объект. ## 5. Commercial Accounting

Домен с наибольшим расхождением между «формулы верны» и «архитектура не соответствует таргету»
(`AUDIT/14_ASKUE_GAP_ANALYSIS.md`, `AUDIT/15_RISKS.md`). Требует наиболее осторожной
последовательности (см. [03_IMPLEMENTATION_SEQUENCE.md](03_IMPLEMENTATION_SEQUENCE.md)) —
именно здесь действует прямой запрет Stage 2.5A на «changing financial calculation semantics»
без утверждения владельца.

| Компонент | Решение | Обоснование |
|---|---|---|
| `computeReadingPeriod`/`computeSiteTariffCost`/`scaleByCtRatio` (формулы) | **KEEP** (семантика) + **EXTRACT** (расположение) | Формулы корректны, переиспользуются между UI-таблицей и XLSX-экспортом без расхождений (`AUDIT/03_BACKEND.md`) — сама бизнес-логика не переписывается. Переносится в `domains/commercial/` как есть. |
| Арифметика на `Math.round(x*100)/100` (float) | **KEEP WITH REFACTOR — только для НОВОГО кода** | Прямое требование мастер-промпта — Decimal вместо float. НО: замена в существующих формулах — это изменение семантики расчёта (иное округление на граничных значениях), что явно запрещено Stage 2.5A без утверждения владельца. Решение: **новые** элементы домена (calculations/statements, будущие Revenue-расчёты) сразу на Decimal; ретрофит существующих формул — отдельный, явно утверждённый шаг, не часть текущей реконсиляции. См. ADR-06. |
| Персистентность результата расчёта | **NEW** | Таблиц `calculations`/`statements` нет — расчёт нигде не сохраняется как версионируемая запись (`AUDIT/03`, `AUDIT/05`). Прямое требование таргета. Добавление новой таблицы — не изменение семантики существующего расчёта, а дополнение (запись входа/выхода уже работающей формулы) — не подпадает под forbidden-список. |
| **Regression fixtures на реальных исторических расчётах** | **NEW, ОБЯЗАТЕЛЬНЫЙ ГЕЙТ** перед любой работой над Decimal/персистентностью | Требование добавлено по итогам ревью этой стадии (см. workstream **B** в `04_RISK_REGISTER.md`/`05_ARCHITECTURE_DECISIONS.md`, ADR-06). Берём реальные пары (показание начало/конец, `ct_ratio`, тариф, потребление, стоимость) по уже посчитанным периодам, фиксируем как fixtures, и любая новая реализация домена 5 обязана воспроизводить те же результаты (пока бизнес-правило не менялось явно). Без этого гейта нельзя достоверно отличить рефакторинг от изменения семантики расчёта — а именно это прямо запрещено Stage 2.5A без утверждения владельца. |
| `MeterAssignment(valid_from, valid_to)` (история привязки счётчика к арендатору/объекту) | **NEW** | Не существует — `meters.site_id`/`tenant_name`/`category` хранят только текущее состояние (`AUDIT/05_DATA_AND_DATABASE.md`). Нужно для аудируемых коммерческих расчётов задним числом. |
