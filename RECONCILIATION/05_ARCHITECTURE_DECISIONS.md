### ADR-01 — Форма системы: Modular Monolith + Workers, без микросервисов

**Статус:** CONFIRMED (прямое требование `03_TARGET_ARCHITECTURE.md`, не решение этой стадии).

**Контекст:** Текущая система — один Node-процесс + один Java-воркер (`AUDIT/02_ARCHITECTURE.md`).

**Решение:** Форма не меняется. Микросервисы/Kafka/Redis не вводятся без доказанной необходимости.

**Последствия:** Все следующие ADR предполагают эволюцию ВНУТРИ одного процесса.

**Фаза:** Не применимо (форма зафиксирована сразу).

**Миграция без остановки:** Не требуется — ничего не меняется на этом уровне.

### ADR-02 — СУБД: SQLite остаётся системой хранения

**Статус:** CONFIRMED (Stage 2.5A прямо запрещает «framework/DB replacement as a prerequisite»).

**Контекст:** `better-sqlite3`, один файл `app.db`, WAL-режим (`AUDIT/05_DATA_AND_DATABASE.md`).
Объём (3.2 МБ) и характер нагрузки не создают давления к замене.

**Решение:** SQLite остаётся минимум до тех пор, пока рост числа клиентов/партнёров не создаст
измеримую (не гипотетическую) потребность в конкурентном доступе из нескольких процессов.

**Последствия:** Все домены (включая Partner Network, Revenue) проектируются под SQLite.

**Фаза:** Не применимо.

**Миграция без остановки:** Не требуется.

### ADR-03 — Извлечение `server.js` по доменам методом strangler, не big-bang

**Статус:** PROPOSED.

**Контекст:** Один файл 2778 строк / 83 маршрута, растущий с каждым новым доменом
(`AUDIT/03_BACKEND.md`, `AUDIT/12_TECH_DEBT.md`).

**Решение:** Переносить код в `domains/<name>/` по одному домену за раз, начиная с наименее
рискованного (Metering Core — физический перенос без изменения логики), не переписывая
одновременно несколько доменов.

**Последствия:** Дольше по календарному времени, чем «переписать всё сразу», но каждый шаг
независимо тестируем и обратим (требование Stage 2.5A).

**Фаза:** Phase 1 (Device Core) — первый домен; далее по порядку `03_IMPLEMENTATION_SEQUENCE.md`.

**Миграция без остановки:** `server.js` продолжает быть точкой входа (`app.listen`) на всём
протяжении extraction — переносятся только внутренние модули, публичные маршруты/поведение не
меняются в рамках самого переноса. Каждый перенесённый домен проверяется live (staging-шаг из
ADR-09) перед тем, как следующий домен начинает переноситься.

### ADR-04 — Permission-based авторизация поверх существующей сессионной модели

**Статус:** PROPOSED.

**Контекст:** Сегодня — enum-роли (`admin`/`user` × `master`/`limited`), не permission-based;
нет ролей `PARTNER`/`PARTNER_MANAGER` (`AUDIT/09_AUTH_AND_SECURITY.md`).

**Решение:** Добавить `roles`/`permissions` таблицы НАД текущим механизмом сессий/bcrypt (не
заменяя его) — текущие enum-значения становятся частным случаем новой модели.

**Последствия:** Существующие пользователи/сессии не инвалидируются переходом.

**Фаза:** Phase 4 (Multitenant SaaS/RBAC), до Phase 5 (роль `PARTNER` требует permission-слоя).

**Миграция без остановки:** Новые таблицы вводятся аддитивно; middleware `requireAuth`/
`requireMaster` продолжает работать на старой модели, пока permission-слой не подключён явно к
каждому маршруту по очереди (не одномоментной заменой всех проверок).

### ADR-05 — Протокольный слой Mercury/iRZ не изменяется

**Статус:** CONFIRMED.

**Контекст:** `mercury*.js` — самый зрелый, live-verified код в базе, с уже исправленными
production-багами (`AUDIT/07_RS485_AND_METERS.md`). Мастер-промпт: «Производственные
device/protocol компоненты считать проверенными активами, пока аудит не докажет обратное» —
аудит подтвердил, не опроверг.

**Решение:** Единственное допустимое действие — физический перенос файлов в
`domains/metering/`. Содержимое не трогается.

**Фаза:** Phase 2.

**Миграция без остановки:** Перенос файла + обновление пути `require()` в одном коммите,
проверяется `node --check` + живой опрос счётчика на staging перед деплоем в прод.

### ADR-06 — Financial Calculation Safety: regression-гейт до Decimal/персистентности (workstream B)

**Статус:** PROPOSED, приоритетный.

**Контекст:** Текущая арифметика — float (`Math.round(x*100)/100`), расчёт не персистентен
(`AUDIT/03_BACKEND.md`, `AUDIT/15_RISKS.md` #3). Прямой запрет Stage 2.5A — «changing financial
calculation semantics» без утверждения владельца. Риски — R-06/R-07/R-08/R-09 в
`04_RISK_REGISTER.md`.

**Решение:** Формулы (`computeReadingPeriod`/`computeSiteTariffCost`/`scaleByCtRatio`) не
меняются напрямую. Вместо этого: (1) зафиксировать текущую формулу как эталон, (2) собрать
regression fixtures на реальных исторических расчётах, (3) новая модель домена 5 реализуется
рядом со старой и должна воспроизводить те же результаты на fixtures, (4) только после
подтверждённого совпадения — переход на Decimal для НОВОГО пути расчёта, (5) персистентность
(`calculations`/`statements`) — только для расчётов после перехода, без пересчёта прошлого
задним числом. Полная последовательность — `02_DATA_MIGRATION.md` §3.

**Последствия:** Дольше, чем прямая замена формул, но исключает риск незаметного изменения
сумм, которые клиент уже видел. Partner Commission (50%) физически не может строиться на
нестабильном основании — жёсткая зависимость Phase 5 от завершения этого ADR.

**Фаза:** Phase 3, блокирующий для Phase 5.

**Миграция без остановки:** Старый путь расчёта (`server.js`, текущие функции) продолжает
обслуживать все запросы, пока новая модель не пройдёт весь regression-набор. Переключение —
по фиче-флагу на уровне конкретного объекта/проекта (постепенный rollout), не одномоментная
замена для всех клиентов сразу.

### ADR-07 — Персистентность коммерческого расчёта — только вперёд, не назад

**Статус:** PROPOSED (часть ADR-06, вынесена отдельно ради явности).

**Контекст:** Нет таблиц `calculations`/`statements` — расчёт нигде не сохраняется как
версионируемая запись (входные показания, коэффициенты, тариф, правило округления, результат,
время/версия — требование `03_TARGET_ARCHITECTURE.md`).

**Решение:** Новые таблицы вводятся аддитивно и начинают заполняться только для расчётов,
выполненных ПОСЛЕ ввода в эксплуатацию — не бэкфилл истории задним числом (нет «правильного»
результата, которым можно перезаписать то, что уже показано клиенту).

**Фаза:** Phase 3.

**Миграция без остановки:** Чистое добавление таблиц (`CREATE TABLE`), не затрагивает
существующие запросы/чтения, пока код записи в них не подключён явно.

### ADR-08 — Secrets management: модель хранения + ротация (workstream A)

**Статус:** PROPOSED.

**Контекст:** Секреты продакшн-приложения уже хранятся правильно (файлы вне репозитория,
`chmod 600`, `fs.readFileSync` при старте — `AUDIT/03_BACKEND.md`, `AUDIT/09`). Единственное
нарушение — `CLAUDE.md` (VPS root SSH, почта, SMTP-пароль в открытом виде, риск R-01).

**Решение:** Распространить уже существующий верный паттерн («секрет — файл вне рабочей папки,
не в документации») на `CLAUDE.md`. Дополнительно — **ротация** всех трёх credentials,
независимо от того, что они не попали в git-историю этого репозитория (см. R-13) — сам факт
продолжительного хранения в открытом виде на диске не даёт полной гарантии, что утечки не
произошло по другим векторам.

**Последствия:** Требует обновления `CLAUDE.md` (описание, где теперь искать секреты) и
физической смены паролей на VPS/почте — операционная задача, не архитектурная, но с
архитектурными последствиями (все будущие интеграции обязаны следовать той же модели).

**Фаза:** Phase 0, немедленно, не дожидаясь остального Stage 3.

**Миграция без остановки:** Ротация пароля VPS/почты не требует остановки `irz-web-gpio` —
единственная точка, где текущий пароль используется приложением — сам VPS SSH-доступ
(человеческий, не программный) и SMTP (файл `/root/.irz_smtp_password`, уже отдельно от
`CLAUDE.md`). Обновляется сам пароль + файл на сервере одновременно, без окна простоя.

### ADR-09 — Production/Git/Deployment Lifecycle (workstream C)

**Статус:** PROPOSED.

**Контекст:** До этой сессии — ни git, ни staging, ни CI (`AUDIT/10_DEPLOYMENT.md`). Репозиторий
и продакшн сегодня совпадают побайтово, но это подтверждено вручную, не гарантировано процессом.

**Решение:** `Git → reviewed changes → staging/verify → production → monitored+backup → rollback`
(полная схема — `03_IMPLEMENTATION_SEQUENCE.md` §0). Git уже введён в этой сессии
(`esforhouse-dot/ASKUEaudit`) — это часть решения, уже выполненная, не только план.

**Последствия:** Замедляет каждый отдельный деплой (появляется обязательный staging-шаг), но
резко снижает риск R-10/R-11/R-12 при масштабировании на 12 доменов.

**Фаза:** Phase 0, предпосылка для Phase 1.

**Миграция без остановки:** Staging — параллельный, не заменяющий существующий процесс деплоя
(`paramiko`-скрипты остаются механизмом переноса файлов на прод, staging добавляется ДО него,
не вместо). Продакшн не останавливается ни на одном шаге внедрения этого ADR.

### ADR-10 — Backup & Recovery (workstream D)

**Статус:** PROPOSED.

**Контекст:** Только 2 ручных ad-hoc снапшота `app.db` (29 авг), нет расписания, нет проверенной
процедуры restore, существующие бэкапы — на том же диске, что и сама БД (R-14/R-15/R-16).

**Решение:** Автоматический бэкап по расписанию (минимум ежедневно) + retention-политика +
хранение вне production-сервера + минимум один подтверждённый прогон restore до того, как
процедура понадобится вживую.

**Последствия:** Небольшая постоянная операционная нагрузка (место на диске/во внешнем
хранилище); резко снижает риск полной потери данных всех клиентов.

**Фаза:** Phase 0, жёсткая предпосылка для Phase 3 (миграция БД без бэкапа запрещена явно
Stage 2.5A).

**Миграция без остановки:** SQLite позволяет безопасное копирование через WAL-checkpoint без
остановки процесса — бэкап не требует downtime `irz-web-gpio`.

### ADR-11 — Reliability Investigation: 140 pm2-рестартов (workstream D)

**Статус:** PROPOSED.

**Контекст:** `irz-web-gpio` — 140 рестартов за 61 день, на порядок больше соседнего процесса
(`AUDIT/06_IRZ_MODEMS.md`, `AUDIT/10`, R-17). Причина не установлена read-only аудитом.

**Решение:** Структурированное расследование до начала масштабного extraction (Phase 1+) —
систематически проверить: crash / OOM / uncaught exception / ручной рестарт / деплой /
watchdog / сеть-железо для каждого случая рестарта за доступный период логов. Устранить
корневую причину, не симптом.

**Последствия:** Для АСКУЭ рестарт процесса — не чисто операционная деталь, а потенциальный
пробел в опросе счётчиков (бизнес-значимые данные). Расследование должно явно установить,
объясняется ли текущая частота уже известными и пофикшенными причинами (GPIO-таймаут-гвард,
FK-retry при удалении модема — оба уже в коде, `AUDIT/06`) или есть необъяснимый остаток.

**Фаза:** Phase 0, до начала Phase 1 (иначе новую регрессию extraction сложно отличить от уже
существующей нестабильности).

**Миграция без остановки:** Расследование — чтение логов, не требует изменения кода на первом
шаге. Если причина требует исправления — точечная правка (аналогично уже сделанным фиксам в
`modemState.js`), не архитектурное изменение.

### ADR-12 — `audit_logs` вводится рано (Phase 0/1), не откладывается до Partner Network

**Статус:** PROPOSED.

**Контекст:** Единой таблицы аудита критических действий нет (`AUDIT/09`, `AUDIT/14` — домен 12
~15%). Домены 1 (permissions), 9 (Partner), 10 (Revenue) все выигрывают от готового механизма
с первого дня.

**Решение:** Ввести `audit_logs` + миддлварь для критических действий (смена тарифа, удаление
счётчика, impersonation, сброс пароля) в Phase 0/1, не откладывать до Phase 5.

**Последствия:** Небольшая, но постоянная запись при каждом критическом действии — незначительные
накладные расходы, простой SQLite `INSERT`.

**Фаза:** Phase 0/1.

**Миграция без остановки:** Аддитивная таблица + точечное добавление вызовов логирования в уже
существующие маршруты, по одному за раз — не требует остановки процесса.

### ADR-13 — Git как система контроля версий для всех последующих изменений

**Статус:** CONFIRMED — уже выполнено в этой рабочей сессии, не план.

**Контекст:** До этой сессии — ни локально, ни на сервере (`AUDIT/01_REPOSITORY_MAP.md`,
`AUDIT/10`). Единственная защита от регрессии — ручной `node --check` + внимательное чтение
диффа.

**Решение:** Репозиторий инициализирован и запушен в `esforhouse-dot/ASKUEaudit` (GitHub),
секреты и PII (`CLAUDE.md`, `Доступы.docx`, `diag_modems_out.txt`, `id.txt`) исключены через
`.gitignore` с первого коммита (см. R-13 в `04_RISK_REGISTER.md`).

**Последствия:** Это предпосылка для ADR-03 (strangler extraction) и ADR-09 (production
lifecycle) — без git невозможен review диффа как формальный, а не «на глаз», шаг.

**Фаза:** Выполнено, предшествует Phase 0 остальных решений.

**Миграция без остановки:** Уже выполнено без влияния на продакшн — git существует независимо
от `/opt/irz-web/`, ни один файл на сервере не был затронут введением версионного контроля.
