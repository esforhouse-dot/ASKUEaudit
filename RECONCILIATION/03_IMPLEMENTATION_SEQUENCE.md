## 0. Сначала — жизненный цикл production, а не сама Phase 0 (workstream C)

До того, как в `fetched/` попадёт хоть одна доменная правка ради этой реконсиляции, должен
заработать процесс, при котором изменения **проходят** через контроль, а не сразу оказываются
в проде. Сегодня фактически:

```
Claude / разработчик → правка файла → paramiko-скрипт → /opt/irz-web/ → pm2 restart → "вроде работает"
```

Целевой процесс (не требует новой инфраструктуры — используется уже существующий git):

```
Git (source of truth)
      │
 reviewed changes (diff читается перед деплоем — уже практикуется вручную per CLAUDE.md,
      │             формализуется как обязательный шаг, не как «когда вспомнили»)
      ▼
 staging/test (минимум: второй pm2-процесс на другом порту с копией app.db, ИЛИ
      │        воспроизведение целевого сценария локально — выбор конкретного механизма
      │        не решается этим документом, это отдельное архитектурное решение Phase 0)
      ▼
   verify (node --check уже практикуется; + минимальный regression-набор по мере
      │    появления доменов, начиная с Commercial Accounting — см. 02_DATA_MIGRATION.md §3)
      ▼
 production (тот же деплой-патторн, что и сейчас — paramiko, не меняется)
      │
 monitored + backup (см. §D ниже)
      │
   rollback (git даёт возможность отката кода; для БД — процедура restore из §D)
```

**Важно:** то, что репозиторий сегодня побайтово совпадает с продакшеном (`AUDIT/10_DEPLOYMENT.md`)
— это не сама цель, а полезная временная точка отсчёта (совпадение подтверждено ДО начала
какого-либо параллельного development-процесса). Само по себе совпадение repo≈prod не является
жизненным циклом — жизненный цикл появляется только когда между git-коммитом и продакшеном
встают обязательные review/verify-шаги. Этот раздел фиксирует целевой процесс, но НЕ обязывает
внедрить полноценный CI/CD немедленно — минимальная версия (ручной review диффа + `node --check`
+ staging-прогон перед restart) уже достаточна для начала Phase 1 и может усиливаться
постепенно.

## Phase 0 — Security, backups, observability, audit (роадмап уже называет это первой фазой)

Эта фаза объединяет три из четырёх workstream'ов (A, D и часть C) — не архитектурные решения
по существу продукта, а предпосылки, без которых остальные фазы рискованнее, чем должны быть.

**Workstream A — Secrets & Security:**
- Вынести секреты из `CLAUDE.md` в место вне рабочей папки.
- **Ротация** скомпрометированных credentials (VPS root SSH, почта, SMTP-пароль приложения) —
  обязательна как часть этого же шага, не отдельно и не «если будет время». Обоснование —
  `04_RISK_REGISTER.md`, риск R-01.
- Rate-limiting на `/api/login`.
- Security headers (CSP/HSTS) в nginx.

**Workstream D — Reliability/Backup:**
- Расписание бэкапов `app.db` (не ad-hoc) + retention-политика.
- Подтверждённая, хотя бы раз проверенная процедура restore.
- Отдельное от VPS хранение бэкапов (иначе один инцидент с диском уничтожает и данные, и бэкап).
- Диагностика 140 pm2-рестартов `irz-web-gpio` — структурированное расследование (см.
  `04_RISK_REGISTER.md`, риск R-05), не наугад: определить, что из crash / OOM / uncaught
  exception / ручной рестарт / деплой / watchdog / сеть-железо объясняет каждую категорию, и
  устранить корневую причину, а не симптом.

**Дополнительно (не отдельный workstream, но дёшево и разблокирует остальное):**
- Восстановить `package.json`/lock-файл для `fetched/` из живого сервера, закоммитить.
- Таблица `audit_logs` — вводится здесь, а не в Phase 5, поскольку домены 1/9/10 выигрывают
  от готового механизма с первого дня (см. `01_COMPONENT_DECISIONS.md`, домен 12).

**Критерий готовности Phase 0 — AUTHORITATIVE (owner, 2026-09-09), жёсткий гейт:** все пункты
выше закрыты или явно приняты владельцем как осознанный риск (не молчаливо отложены).
**Декомпозиция `server.js` (Phase 1 и далее) НЕ НАЧИНАЕТСЯ до завершения Phase 0** — это не
рекомендация, а обязательное условие, утверждённое владельцем. Ни одна задача `P1-*` (см.
`IMPLEMENTATION_PLAN/`) не может быть исполнена раньше подтверждённого закрытия всех задач
`P0-*`.
