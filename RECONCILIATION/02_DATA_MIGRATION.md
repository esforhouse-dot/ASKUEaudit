## 2. Механика миграций — когда менять паттерн

Текущий inline-паттерн (`PRAGMA table_info` + `ALTER TABLE ADD COLUMN`, каждое изменение с
развёрнутым комментарием прямо в `db.js`) работает и достаточно прозрачен на сегодняшнем
масштабе (`AUDIT/05`, `AUDIT/12`). **Решение: не заменять его сейчас.** Ввести отдельный
migration-раннер (нумерованные файлы, таблица `schema_migrations`) как отдельное решение
**в момент, когда** количество новых таблиц одной итерации превышает ~5-6 (ожидаемо — Partner
Network, Phase 5, добавляет 8 таблиц разом) — то есть заранее готовиться к этому переходу при
подготовке Phase 5, не изобретать раньше срока.

## 3. Самая чувствительная миграция: Commercial Calculation (workstream B)

Это единственный участок данных, где ошибка не просто ломает функциональность, а меняет суммы,
которые видит клиент. Обязательная последовательность (не сокращать, не переставлять шаги):

```
1. Зафиксировать СУЩЕСТВУЮЩУЮ формулу как есть (computeReadingPeriod/computeSiteTariffCost/
   scaleByCtRatio, server.js — уже задокументировано в AUDIT/03_BACKEND.md)
        ↓
2. Собрать regression fixtures: реальные пары (meter_id, период, ct_ratio, тариф) →
   (показание начало, показание конец, потребление, стоимость) по уже прошедшим периодам,
   взятые из живых данных (read-only снятие, не изменяет БД)
        ↓
3. Новая Commercial Calculation модель (домен 5) реализуется РЯДОМ со старой, проверяется
   регрессионно против fixtures из шага 2 — результат обязан совпадать (в пределах округления)
   при неизменном бизнес-правиле
        ↓
4. Только после совпадения — переход на Decimal-арифметику для НОВОГО пути расчёта
        ↓
5. Historical tariff model (valid_to у site_tariffs) — аддитивно, не переписывает прошлое
        ↓
6. Сохранённые входные данные + сохранённый результат (calculations/statements) — начинают
   записываться для НОВЫХ расчётов; расчёты периодов ДО перехода не пересчитываются задним
   числом (нет «правильного» результата, которым можно перезаписать то, что уже показано
   клиенту и, возможно, уже стало основанием реального счёта/оплаты)
        ↓
7. Новый Decimal-путь работает В ПРОДЕ параллельно со старым float-путём минимум один полный
   биллинговый цикл, результаты обоих путей сверяются на реальном трафике (не только на fixtures)
        ↓
8. **AUTHORITATIVE (owner, 2026-09-09) — Definition of Done, уточняет ADR-06:** после
   подтверждённого совпадения на шаге 7 новый Decimal-путь становится ЕДИНСТВЕННЫМ production
   calculation path, старый float-путь **удаляется** из кода. Две параллельные системы
   денежного расчёта не поддерживаются бессрочно — это переходное состояние шага 7, не
   постоянная архитектура.
        ↓
9. Только после шага 8 — фундамент для Revenue Event → Partner Commission (50%) →
   Partner Balance → Payout (домены 9-10). Partner Network НЕ начинается, пока шаги 1-8
   не завершены и не подтверждены владельцем.
```

Это прямая реализация требования, сформулированного при ревью этой стадии: «существующие
коммерческие расчёты должны быть воспроизводимыми и регрессионно проверяемыми до миграции на
новую модель», а шаг 8 — уточнённого владельцем (2026-09-09) Definition of Done для ADR-06:
старый float-путь не остаётся навсегда — после подтверждённого совпадения он удаляется.

## 4. Предпосылки до любой миграции (без исключений)

Ни один из шагов §1/§3 не выполняется, пока не закрыто (workstream **D**, подробности —
[04_RISK_REGISTER.md](04_RISK_REGISTER.md)):
- Работающий, проверенный backup `app.db` (не ad-hoc снапшот вручную — расписание + retention).
- Подтверждённая процедура restore (не только «бэкап создаётся», но и «бэкап реально
  разворачивается обратно» — проверено хотя бы раз на копии).
- Миграция выполняется на staging-копии БД первой, живая `app.db` — только после проверки на копии.
