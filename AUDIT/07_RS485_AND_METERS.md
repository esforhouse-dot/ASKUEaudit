# 07 — RS-485 AND METERS (Mercury protocol)

Это самый зрелый слой кодовой базы — четыре файла (`mercuryProtocol.js`, `mercuryPoll.js`,
`mercuryProfile.js`, `mercuryProfilePoll.js`), сами по себе уже написаны в
evidence-labeled стиле (ссылки на официальный протокол INCOTEX, независимые PHP-реализации
для сверки, явные пометки «проверено живьём [дата] на [объект]»). Ниже — то, что
подтверждено чтением всех четырёх файлов целиком.

## Транспорт

TCP напрямую на «прозрачный порт» iRZ Collector (не через демон/MySQL-очередь, в отличие от
GPIO-канала — отдельный физический путь, см. [02_ARCHITECTURE.md](02_ARCHITECTURE.md)).
Одно постоянное соединение на весь цикл опроса одного счётчика — открывать новое соединение
на каждую команду прямо запрещено комментарием в коде (ответ может прийти с опозданием и
попасть в следующее соединение). CONFIRMED.

## Протокол

- Кадр: `[адрес 1 байт][команда...][CRC16 LSB][CRC16 MSB]`, CRC16-MODBUS (таблица захардкожена,
  стандартная). Многобайтовые значения — little-endian, с задокументированным исключением у
  параметра `00h` (серийный номер/дата выпуска) — RAW-десятичное значение байта, не nibble-BCD.
  CONFIRMED (`mercuryProtocol.js`, реализация + комментарии со сверкой на официальном примере
  протокола: "29 5A 40 43" → серийный "41906467").
- Заявленная совместимость: линейка Меркурий 203.2TD/204/208/230/231/234/236/238 (по формату
  кадра). **Живьём проверено только на одном экземпляре Меркурий 234** (adr=29, pass=111111) —
  сам код честно об этом предупреждает (docstring в шапке `mercuryProtocol.js`, а также
  `CLAUDE.md`). PARTIALLY CONFIRMED — протокол общий по документации, но не multi-model-tested.

## Реализованные команды (используемые в проде)

| Код | Назначение | Где парсится |
|---|---|---|
| `00h` (ping) | поиск/проверка адреса на шине | `cmdPing`/`scanBus` |
| `01h` (connect) | авторизация (уровень+6-цифр пароль) | `cmdConnect` |
| `08h`+`00h` | серийный номер + дата выпуска (единственная команда без открытия канала) | `cmdSerial`/`parseSerial` |
| `08h`+`16h`+`A0h` | сводное чтение мгновенных величин (P/Q/S, U, I, cosφ, частота) одним ответом | `cmdInstant`/`parseInstant` — верифицировано сверкой U·I·cosφ на объекте Capitalservis |
| `05h` | накопленная энергия по тарифам (A+/A-/R+/R-) | `cmdEnergy`/`parseEnergy16` |
| `06h`/`16h` | профиль средних мощностей (получасовки), абсолютная/относительная адресация | `mercuryProfile.js` |
| `08h`+`2Fh`+`00h` | текущие зафиксированные флаги событий/тревог | `cmdEventFlags`/`parseEventFlags` |
| `04h` | запись именованного журнала (события с реальным временем, до 10 записей) | `cmdJournalRecord` + `parseJournalPair`/`parseReprogramRecord` |
| `08h`+`17h` | состояние тарификатора | `cmdTariffState` — помечено в коде как «предварительный разбор, не перепроверен живьём отдельно» |
| `08h`+`12h`+`00h` | вариант исполнения (постоянная счётчика A, число фаз, наличие профиля) | `cmdVariant`/`parseVariant` |

Все привязки к реальным проверкам (объект, дата) задокументированы прямо в коде — это
исключительно сильное свойство для аудита: по сути, каждая функция протокола уже несёт
собственный evidence-label. CONFIRMED чтением.

## Известное НЕ работающее — задокументированная в коде находка

`cmdResetEventFlags` (`03h/2Fh/02h` — запись флагов сброса событий) **реализована, но
подтверждённо не работает** — счётчик не отвечает на этот кадр (проверено живьём 25 авг,
согласно комментарию в коде). Функция оставлена в модуле как задел, **не вызывается** из
продового кода — квитирование тревог сделано полностью на своей стороне
(`meters.ack_event_bits` в SQLite, сравнение битовых масок через `eventsToBitmask`), без
обращения к счётчику. CONFIRMED — grep подтверждает, что `cmdResetEventFlags` экспортируется,
но не импортируется/не вызывается ни в `server.js`, ни где-либо ещё.

## Алгоритм обхода профиля (offset-based, не по адресу «последней записи»)

Параметр `13h` (адрес последней записи) сознательно **не используется** как источник истины —
в коде явно объяснено, что это поле может указывать на устаревшие данные (подтверждено дважды
на реальном счётчике). Вместо этого `mercuryProfilePoll.js` идёт от текущего момента назад по
относительному смещению (`16h`), по одной записи за раз, и останавливается по одному из трёх
условий: `caught-up` (дошли до уже известной в БД даты+слота — определяется вызывающим кодом
`server.js`, не протоколом), `discontinuity` (разрыв непрерывности между соседними записями —
с ретраями на подтверждение, чтобы не спутать затор на шине с реальным разрывом истории),
`max-records` (упёрлись в лимит). CONFIRMED, логика прочитана целиком — это тот самый механизм,
для которого в памяти проекта зафиксирован баг-фикс 5 сентября (пропуск смещения при промахе
ломал непрерывность) — **текущий код уже содержит исправленную версию** (явный ретрай-цикл
`READ_RETRIES`/`CONTINUITY_RETRIES` вместо `continue`, с комментарием, объясняющим именно
эту историю бага). CONFIRMED as fixed.

## Self-energy гибрид

Помимо профиля (`06h/16h`, получасовки самого счётчика), отдельно считается «самозапись»
(`kwh_self`) — дельта между последовательными опросами накопленной энергии (`05h`), нужна для
моделей счётчиков, где профиль недоступен/не работает (упомянут Меркурий 230 как пример).
Хранится в отдельной колонке `readings.kwh_self`, не смешивается с `kwh` (иначе задвоение при
совпадении часа). Источник для отображения выбирается на чтении: `kwh`, если есть, иначе
`kwh_self` (`COALESCE`, см. также [05_DATA_AND_DATABASE.md](05_DATA_AND_DATABASE.md)).
Разрыв между опросами энергии классифицируется в WARN (одна пропущенная итерация — штатно,
помечается `incomplete_self`) / MAX (несколько часов простоя — точка отсчёта просто
сдвигается, дыра не восстанавливается задним числом, аналогично поведению профиля при
простое демона). CONFIRMED, `server.js` (applySelfEnergy — не читан построчно в рамках этого
прохода, но описание в `db.js`-комментариях и `CLAUDE.md` совпадает с поведением, наблюдаемым
в остальном коде).

## Settle-таймауты — намеренная оптимизация

Короткие фиксированные ответы (пинг, connect, чтение записи журнала/профиля по одной записи)
используют `settleMs≈200` вместо дефолтных 900мс — экономия в сценариях с десятками
последовательных запросов (журнал событий — 40 запросов на полную историю; первая догрузка
профиля — тысячи записей). Сводная команда мгновенных величин (`16h/A0h`, 89 байт, самый
крупный ответ) сознательно **не** переведена на короткий settle — в коде явная пометка «не
проверяли на такой задержке, риск обрезать самый ценный поток данных того не стоит».
CONFIRMED — согласуется и с `CLAUDE.md`, и с фактическим кодом.

## Многосчётчик на одной шине

Несколько ПУ на одной физической паре RS-485 работают параллельно через общую приоритетную
очередь `serializeFor` (см. [02_ARCHITECTURE.md](02_ARCHITECTURE.md)/
[06_IRZ_MODEMS.md](06_IRZ_MODEMS.md)) — не заменяют друг друга, опрашиваются по кругу.
Скан шины ищет все отвечающие адреса в диапазоне 0-239 (`scanBus`). CONFIRMED.
