## Слой очередей/состояния — `modemState.js`

Два независимых механизма сериализации на общий физический ресурс (см. подробнее
[02_ARCHITECTURE.md](02_ARCHITECTURE.md)):
- `serializeFor(modemId, fn, {priority})` — шина RS-485 (счётчики), приоритетная очередь hi/lo.
- `serializeGpioFor(modemId, fn, timeoutMs=30000)` — канал модема (GPIO/CSQ/LBS/USSD через MySQL
  `irzserver4`), с гонкой против таймаута внутри самой цепочки (не только на call site) —
  предотвращает перманентное зависание всей очереди при подвисшем `pool.execute()`.
CONFIRMED — фикс от 2026-09-02 подтверждён чтением текущего кода (`Promise.race` внутри
`serializeGpioFor`, `modemState.js:88-96`), соответствует памяти `irz-known-issues-2026-08-26.md`.

## Money-логика (коммерческий расчёт)

`computeReadingPeriod()`, `computeSiteTariffCost()`, `scaleByCtRatio()` (`server.js:1704-1769`).
- Показания на начало/конец периода выводятся не из истории, а **обратным счётом** от текущего
  живого показания счётчика (`meters.last_energy_kwh`) минус сумма расхода после конца периода.
  Осмысленное решение (переживает рестарт процесса, не зависит от in-memory кэша), но означает,
  что «показание на конец периода» — вычисляемая, а не хранимая величина.
- Тариф — история с `valid_from` (без `valid_to`; действующая ставка на дату определяется как
  последняя `valid_from <= date`) на объект (`site_tariffs`), с корректным разбиением периода
  на сегменты при смене ставки внутри периода. CONFIRMED, логика читана целиком.
- Округление — `Math.round(x * 1000) / 1000` (кВт·ч, до 0.001) и `Math.round(x * 100) / 100`
  (₽, до копеек) — обычная JS floating-point арифметика, не Decimal/BigInt. Прямое расхождение
  с принципом мастер-промпта «не использовать JS floating point для финансовой логики». См.
  [15_RISKS.md](15_RISKS.md) для оценки серьёзности.
- **Ни один расчёт не сохраняется** как отдельная запись с версией/меткой времени/использованными
  коэффициентами — при каждом обращении к `/api/objects/table` или `/api/objects/export`
  результат вычисляется заново из текущих `readings`+`site_tariffs`+`ct_ratio`. NOT FOUND —
  таблицы `calculations`/`statements` в схеме нет.

## Обработка ошибок

Паттерн единообразный: `.catch(e => res.status(500).json({ error: e.message }))` на
промис-цепочках, синхронные — `try/catch` вокруг `db.transaction`. Стектрейсы клиенту не
утекают (только `e.message`). Логирование ошибок — `console.error`, попадает в `pm2 logs`;
структурированного логирования/APM нет (см. [12_TECH_DEBT.md](12_TECH_DEBT.md)).
