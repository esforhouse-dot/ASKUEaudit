# 13 — REUSABLE COMPONENTS (classification)

Классификация по шкале из Stage 2: KEEP AS IS / KEEP WITH REFACTOR / EXTRACT / REWRITE /
DEPRECATE / UNKNOWN. Это входные данные для формального решения на Stage 2.5A, не само
решение.

## KEEP AS IS

**`mercuryProtocol.js` / `mercuryPoll.js` / `mercuryProfile.js` / `mercuryProfilePoll.js`**
(протокольный слой Меркурий). Мастер-промпт прямо предписывает: «Производственные
device/protocol компоненты считать проверенными активами, пока аудит не докажет обратное» —
этот аудит подтверждает, а не опровергает: код зрелый, evidence-labeled самим собой,
live-verified на реальном приборе, содержит задокументированные и уже исправленные баги
(offset-skip при промахе, GPIO-таймаут). Единственная реальная оговорка — protocol
multi-model coverage (проверено только на одном экземпляре 234-й модели) — это не повод
переписывать, а повод расширять тестовым покрытием при появлении второго типа счётчика.

**`esc()` HTML-escape + `sanitizeInlineHtml()`** — простой, последовательно применяемый
XSS-барьер. Нет причин трогать при переходе на любую будущую архитектуру фронтенда — этот
паттерн (экранирование на выводе + санитайз пользовательского HTML на входе) универсален.

**Секреты вне исходника** (`fs.readFileSync('/root/.irz_*_password')`) — паттерн стоит
буквально скопировать при добавлении новых интеграций (Partner-домен, любые будущие внешние
API), а не изобретать заново.

## KEEP WITH REFACTOR

**`auth.js`** — сама механика (bcrypt + собственные сессии в SQLite, `HttpOnly/Secure/
SameSite=Lax`) корректна и её не нужно выкидывать. Требует расширения: роли сегодня —
enum на 2 уровня (`admin`/`user` × `master`/`limited`), таргет — 5 ролей
(`PLATFORM_ADMIN`/`MASTER`/`USER`/`PARTNER`/`PARTNER_MANAGER`) с permission-based моделью.
Это не переписывание механизма сессий, а добавление слоя permissions поверх уже рабочей
аутентификации.

**`modemState.js`** (очереди `serializeFor`/`serializeGpioFor`) — сам факт приоритетных
очередей на общий физический ресурс (RS-485/MySQL-канал) с таймаут-гвардами — верно
спроектированный, живьём проверенный паттерн (задокументированные фиксы двух реальных
production-инцидентов). Требует рефакторинга только в части персистентности: сегодня все
очереди/кэши — исключительно in-memory (`Map`), полностью теряются при рестарте процесса
(что само по себе нормально для очереди операций, но означает отсутствие Device Core
абстракции «last successful reading»/«communication gaps» как персистентных сущностей,
которые требует таргет-архитектура — эта персистентность частично есть в `meters.last_energy_at`
и `readings`, частично отсутствует как явный домен).

**`db.js`** (схема + inline-миграции) — сама схема добротная (WITHOUT ROWID для upsert-грида,
исторические тарифы, широко закомментированный inline-migration-паттерн). Нуждается в
рефакторинге при масштабировании на 12 доменов таргет-архитектуры: единый файл с
последовательными `ALTER TABLE IF NOT EXISTS`-проверками не выдержит роста количества таблиц
(Partner Network + Revenue + AI добавят десятки новых сущностей) без выделения в отдельные
migration-файлы/раннер.

**Тарифная/коммерческая логика** (`computeReadingPeriod`/`computeSiteTariffCost`/
`scaleByCtRatio`) — бизнес-логика корректна и уже разделяет ответственности разумно
(отдельная функция на каждый шаг, переиспользуется между UI-таблицей и XLSX-экспортом, чтобы
не разойтись в цифрах — хороший знак дисциплины). Требует REFACTOR по двум осям: перейти на
Decimal-арифметику и добавить персистентный слой `calculations`/`statements` (см.
[03_BACKEND.md](03_BACKEND.md)/[15_RISKS.md](15_RISKS.md)) — не переписывание формул, а
изменение того, как и где хранится их результат.

## EXTRACT

**`server.js` как единица** — сама бизнес-логика внутри в основном качественная (см. выше),
но физическая организация «всё в одном файле» — первый кандидат на разбиение по доменам
(routes/, mercury domain, objects/commercial domain, reports domain, gpio domain, alerts
domain) до того, как в него начнут добавляться Partner Network/Revenue/AI-маршруты. Это не
REWRITE — большая часть функций уже достаточно самодостаточна (принимает `req`/явные
параметры, не тянет скрытое глобальное состояние сверх `state`/`db`), extract == перенос
существующего кода в модули с сохранением поведения, не переписывание логики.

## REWRITE

Кандидатов на полное переписывание в текущем аудите **не найдено**. Ни один просмотренный
компонент не выглядит настолько порочным по конструкции, чтобы дешевле было переписать с
нуля, чем рефакторить — это редкий и хороший результат для аудита такого масштаба задачи.

## DEPRECATE

**`modem_tariffs` таблица** — заменена `site_tariffs`, оставлена только ради обратной
совместимости с историческими данными существующих проектов. Кандидат на явное списание
(с разовым ручным переносом нужных исторических ставок, если они есть) на Stage 2.5A.

**`cmdResetEventFlags`/`03h/2Fh/02h`** (сброс флагов события записью на сам счётчик) —
подтверждённо не работает, уже не вызывается из продового кода, оставлена как экспортируемая,
но мёртвая функция с пометкой "задел". Не критично, но можно либо удалить, либо явно
пометить `@deprecated` при следующей плановой правке `mercuryProtocol.js`.

**Диагностические `mercury-*.js`/`*-test.js` файлы на сервере вне репозитория** — см.
[12_TECH_DEBT.md](12_TECH_DEBT.md), решение — за пользователем (забрать или удалить).

## UNKNOWN

**Корневое приложение `irz-modem-control` целиком** (`server.js` в корне, `public/`,
`ecosystem.config.js`) — сознательно не входит в область этого аудита (задача Stage 2 и
мастер-промпт формулируют цель вокруг мультитенантной SaaS-платформы, каковой является
`fetched/`, не старый прототип). Классификация статуса (используется ли ещё живыми клиентами,
или это чисто исторический артефакт, который можно списать) требует явного ответа
пользователя — код на сервере работает (pm2 online, порт 3004), но это не то же самое, что
«нужен ли он бизнесу дальше». Оставлено как UNKNOWN намеренно — не в компетенции read-only
аудита кода принимать это решение.
