# 12 — TECH DEBT

Отсортировано по практическому влиянию на способность безопасно наращивать таргет-архитектуру
(не по субъективной «важности»).

## 1. Нет версионного контроля (git)

Ни локально, ни на сервере. История решений живёт только во внешней памяти ассистента
(`MEMORY.md`/`irz-*.md`) и в комментариях самого кода — оба источника хорошего качества, но
ни один не даёт: diff между версиями, blame по строке, откат к произвольному коммиту, ветки
для параллельной разработки, PR-ревью, автоматический CI. Это первое, что обычно блокирует
командную разработку и то, что предполагает Roadmap (Phase 1-7, множество последовательных,
но местами параллельных доменов). CONFIRMED. Не в объёме Stage 2 — исправлять, но стоит
явно решить на Stage 2.5A/при планировании имплементации, а не откладывать неявно.

## 2. Нет автотестов

Ни unit, ни integration, ни e2e. Нет тестового фреймворка в зависимостях (ни prod, ни dev).
Единственная сегодняшняя защита от регрессии — `node --check` (только синтаксис) + ручной
живой прогон перед/после деплоя. Для протокольного слоя (Меркурий) это отчасти компенсируется
диагностическими скриптами (`profile-test.js`, `energy-test.js` и др.) — но это ручные
инструменты для интерактивной проверки, не автоматический regression suite. CONFIRMED.
При росте кода под Commercial Accounting/Partner Network (денежные расчёты, комиссии) риск
тихой регрессии в бизнес-логике станет заметно дороже, чем сейчас в Device/Metering слое.

## 3. `server.js` — монолитный роут-файл (2778 строк / 83 маршрута)

Один файл содержит: конфигурацию, работу с демоном, все 83 HTTP-маршрута, фоновые задачи,
бизнес-логику коммерческого расчёта, генерацию XLSX, работу с email. Нет деления по доменам
на уровне файлов/модулей (в отличие от, например, слоя Mercury, который уже правильно
разделён на 4 файла по ответственности). PARTIALLY CONFIRMED as debt — код внутри читаем и
последовательно закомментирован, проблема не в качестве отдельных функций, а в том, что весь
таргетный список доменов (Identity, Organizations, Device Core, Metering Core, Commercial
Accounting, Tariffs, Reporting, Incidents, Partner Network, Revenue, AI, Audit) при текущей
структуре продолжил бы расти в один и тот же файл. Это первый практический кандидат на
EXTRACT при Stage 2.5A — не потому что код плохой, а потому что 12 доменов в одном файле
физически не будет читаемым.

## 4. Денежная арифметика на плавающей точке

`Math.round(x*100)/100`, `Math.round(x*1000)/1000` по всей коммерческой логике — не Decimal/
BigInt. Подробно — [03_BACKEND.md](03_BACKEND.md), оценка риска — [15_RISKS.md](15_RISKS.md).

## 5. Коммерческий расчёт не персистентен

Вычисляется на лету, не хранится как версионируемая запись. Подробно —
[03_BACKEND.md](03_BACKEND.md)/[05_DATA_AND_DATABASE.md](05_DATA_AND_DATABASE.md).

## 6. Нет `package.json` для `fetched/` в репозитории

Единственный источник правды о зависимостях текущего продукта — живой сервер, не репозиторий.
Подробно — [10_DEPLOYMENT.md](10_DEPLOYMENT.md)/[11_DEPENDENCIES.md](11_DEPENDENCIES.md).

## 7. Дрейф диагностических файлов между сервером и репозиторием

`/opt/irz-web/mercury/mercury-connect-probe.js`, `mercury-read.js`, `mercury-test.js`
существуют только на сервере — написаны/оставлены там напрямую в процессе живой отладки,
никогда не забраны обратно в репозиторий. Не влияют на работу приложения (не импортируются
`server.js`), но означают, что «репозиторий = продакшн» верно не абсолютно, а только для
файлов, которые реально участвуют в HTTP-приложении. CONFIRMED (md5sum-сверка, см.
[10_DEPLOYMENT.md](10_DEPLOYMENT.md)). Низкий приоритет — рекомендация: либо забрать их в
`fetched/` (если ещё полезны для будущей отладки других моделей счётчиков), либо удалить
с сервера явным решением пользователя (не в рамках read-only аудита).

## 8. Ручной inline-паттерн миграций БД

Работает и хорошо задокументирован построчно, но не масштабируется на количество доменов из
таргет-архитектуры без выделения в отдельный migration-runner. Подробно —
[05_DATA_AND_DATABASE.md](05_DATA_AND_DATABASE.md).

## 9. Устаревшая, но не удалённая таблица `modem_tariffs`

Заменена `site_tariffs` (31 авг), не удалена и не мигрируется автоматически — осознанное
решение (в коде явный комментарий, почему автоматическая миграция неоднозначна), но по факту
это мёртвый код/данные, которые будущий читатель схемы может принять за активный источник.
NOT a bug, но стоит явно списать (DEPRECATE) на Stage 2.5A, если исторические тарифы по
старым проектам больше никому не нужны, либо разово перенести вручную.

## 10. Нет rate-limiting на login, нет CSP/HSTS

Оба — недорогие в исправлении, оба подробно разобраны в
[09_AUTH_AND_SECURITY.md](09_AUTH_AND_SECURITY.md).

## 11. Логирование — `console.log`/`console.error` в pm2 logs, без структуры

Нет structured logging (JSON-логи), нет APM/трейсинга, нет метрик (кроме дефолтных
pm2/pm2-plus счётчиков memory/cpu/restarts, видных в `pm2 jlist`). Для одного процесса и
текущего масштаба этого достаточно для ручной диагностики (что и происходит на практике,
судя по памяти проекта — диагностика идёт через `pm2 logs`), но при росте станет узким
местом для observability (Phase 0 роадмапа явно называет observability одной из целей).

## 12. Мусор в корне репозитория

`_patch2.js`, `diag_modems_out.txt`, `id.txt`, `verify_journals_out2.txt` — разовые
файлы-выгрузки в корне, не относящиеся однозначно ни к `fetched/`, ни явно описанные в
`CLAUDE.md`. Низкий приоритет, не мешает работе, но замусоривает `ls` корня. UNKNOWN
происхождение точное — не исследовалось подробно (вне текущего продукта).
