# 09 — AUTH AND SECURITY

## Модель аутентификации

Собственная реализация (не `express-session`/`passport` — осознанный выбор, задокументирован
в комментарии `auth.js:1`): bcrypt-хэши паролей (`bcryptjs`, cost factor 10) + свои сессии в
SQLite (`sessions` таблица, 30-дневный TTL, токен — `crypto.randomBytes(32).toString('hex')`).
Cookie: `askue_sid`, `HttpOnly; Secure; SameSite=Lax; Path=/`. CONFIRMED, `auth.js` прочитан
целиком (121 строка).

## Модель ролей (как есть, а не как в таргет-архитектуре)

Двухуровневая, не permission-based:
- **Платформенный уровень**: `admins` таблица, роль `'admin'` в сессии — эквивалент
  `PLATFORM_ADMIN` из таргета. Может: управлять проектами, пользователями, объектами
  (`sites`), импersonate любой проект.
- **Уровень проекта**: `users` таблица, роль `'user'` в сессии + `access_role` ∈
  {`'master'`, `'limited'`}. `master` — полный доступ в рамках своего проекта (эквивалент
  `MASTER`/`USER` из таргета, слитых воедино). `limited` — жёстко ограничен на бэкенде
  allow-list префиксов путей (`/api/me`, `/api/logout`, `/api/context`, `/api/objects`) —
  **не только скрытие кнопок на клиенте**, а серверная проверка (`server.js:976-983`),
  что исключает обход через devtools. CONFIRMED, оба слоя прочитаны целиком.

Ролей `PARTNER`/`PARTNER_MANAGER` из таргет-архитектуры **не существует** — ни таблиц, ни
кода. NOT FOUND. Авторизация — enum-based (`CHECK(role IN ('admin','user'))`,
`access_role TEXT`), не permission-based, как рекомендует `03_TARGET_ARCHITECTURE.md`
(«Предпочтение permission-based authorization вместо набора boolean-флагов») — прямое
расхождение, ожидаемое на этой стадии продукта (для 2 ролей enum проще и оправданно; при
добавлении Partner-доменов текущая модель потребует переосмысления, не косметического
расширения enum'а).

## Tenant isolation

Централизованный middleware-паттерн (см. также [02_ARCHITECTURE.md](02_ARCHITECTURE.md)):
`req.projectId` выводится только из подписанной серверной сессии (никогда из клиентского
ввода), затем `req.modem` резолвится строго `WHERE project_id = ?`, `req.meter` — строго
`WHERE modem_id = ?` (даже если `meterId` пришёл в query-параметре от клиента — он
используется только как фильтр внутри уже отфильтрованного по проекту модема, не как
самостоятельный источник доступа). Попытка подставить чужой `meterId` в query даст пустой
результат, не чужие данные. CONFIRMED чтением `server.js:1240-1249`, это соответствует
описанному в `CLAUDE.md` дизайну и проверяется логикой SQL-запроса напрямую (не полагается
на «доверие» к параметру).

Ограничение: middleware резолвит **один** активный модем на проект (`ORDER BY id LIMIT 1`) —
если в будущем один проект/объект будет физически иметь несколько модемов одновременно
(отдельные здания на одном юрлице?), этот паттерн потребует пересмотра, не является багом
сейчас (сегодняшняя продуктовая модель — 1 модем на объект). См. также [05](05_DATA_AND_DATABASE.md).

### Находка: секреты в `CLAUDE.md`

`CLAUDE.md` (документация для ассистента, лежит в корне рабочей папки) содержит в открытом
виде: пароль root-доступа по SSH к VPS, пароль входа в почтовый ящик `irz_dir2@mail.ru`,
пароль внешнего приложения для SMTP. Это прямо противоречит собственному принципу мастер-промпта
(«Секреты, пароли, API keys и production credentials никогда не помещать в документацию,
логи или git») — и что важно, реализация на сервере этот принцип как раз **соблюдает**
(секреты в отдельных `chmod 600` файлах, не в исходнике) — расхождение конкретно в этом одном
документе-заметке, не в архитектуре продукта. Репозиторий не является git-репозиторием
сейчас (риск публикации через git отсутствует), но:
- Файл может синхронизироваться облачными сервисами/бэкапами рабочего стола.
- Любой процесс/сессия/агент с доступом к файловой системе читает эти секреты без всякого
  барьера.
- Если репозиторий когда-либо будет инициализирован под git и случайно запушен — секреты
  уйдут в историю немедленно.

Значения секретов **не воспроизводятся** в этом аудите (только тип и локация, как предписано
Stage 2). Рекомендация: вынести SSH/почтовые пароли из `CLAUDE.md` в отдельный файл вне
рабочей папки (или менеджер паролей) и оставить в `CLAUDE.md` только ссылку на то, где искать —
той же моделью, что уже используется для секретов приложения на сервере.

### Пароль счётчика Меркурий в открытом виде — отдельная, менее критичная находка

`meters.password` хранится как plain TEXT в `app.db`, не хэшируется. Оценка риска — НИЗКАЯ:
это 6-значный numeric-код доступа к самому физическому счётчику (обычно `111111` по
умолчанию, согласно `mercuryProtocol.js`), а не пароль учётной записи человека; приложению
физически необходимо знать это значение в открытом виде, чтобы подключаться к прибору
(bcrypt здесь неприменим — это не проверка равенства, а передаваемый секрет). NOT a
misconfiguration, но стоит зафиксировать как осознанный компромисс, а не забытый недосмотр.

## Login — устойчивость к перебору

`POST /api/login` — **не найдено** ограничения по частоте попыток (rate limiting), блокировки
по IP/логину, CAPTCHA. NOT FOUND (grep по requires — нет `express-rate-limit`/аналогов; сам
маршрут прочитан целиком, счётчика попыток нет). Единственное встроенное замедление — стоимость
самого bcrypt-сравнения (cost 10, доли секунды на попытку) — недостаточно против
распределённого перебора. CONFIRMED gap, MEDIUM severity (см. [15_RISKS.md](15_RISKS.md)).

## CSRF, XSS, security headers

- CSRF: нет явного токена; смягчается `SameSite=Lax` + отсутствием CORS-разрешений для
  сторонних origin'ов + требованием `Content-Type: application/json` на все изменяющие запросы.
  Подробнее — [04_FRONTEND.md](04_FRONTEND.md). INFERRED риск как низкий, не верифицировано
  живым PoC.
- XSS: последовательный `esc()` на клиенте + `sanitizeInlineHtml()` на сервере для
  пользовательского HTML лендинга. CONFIRMED, KEEP AS IS.
- HTTP security headers: `X-Frame-Options: SAMEORIGIN`, `X-Content-Type-Options: nosniff`
  выставлены на уровне nginx (`nginx-askue.conf:15-16`). НЕ найдено: `Content-Security-Policy`,
  `Strict-Transport-Security` (HSTS), `Referrer-Policy`. NOT FOUND — умеренный gap, не
  критичный для внутреннего B2B-кабинета без пользовательского контента от третьих лиц, но
  стоит закрыть недорого при следующей правке nginx-конфига.

## SQL/command injection

Параметризованные запросы `db.prepare(...)` везде в SQLite-слое — конкатенации SQL-строк из
пользовательского ввода не найдено (просмотрен весь `server.js`). Команды к модему/USSD —
через allow-list/приведение типов, не конкатенацию произвольных строк в shell/AT-команды
(см. [08_GPIO.md](08_GPIO.md)). `child_process.spawn('java', [...])` — аргументы фиксированы
в коде, не зависят от пользовательского ввода. CONFIRMED — SQL/command injection поверхность
практически закрыта в проверенных маршрутах.

## Аудит-трейл действий

Частичный: `alerts.ack_at` (кто/когда квитировал тревогу — хотя фактически пишется только
метка времени, не actor_id, judging by schema — PARTIALLY CONFIRMED, не проверялся route-код
квитирования построчно на предмет записи actor'а), `report_log` (лог отправленных отчётов).
**Нет общей таблицы `audit_logs`** для действий вроде смены тарифа, удаления счётчика,
импersonation, сброса пароля — таргет-архитектура требует audit trail на «критические
действия» явно. NOT FOUND как единая сущность — сегодня история таких действий не
восстановима постфактум (кроме что можно вывести из `sessions`/`created_at` полей отдельных
таблиц, что не то же самое, что журнал событий).
