# Восстановление `app.db` из бэкапа — процедура

P0-06 (`RECONCILIATION/04_RISK_REGISTER.md` R-15). Для человека в реальной ситуации, не для
чтения кода — короткая, по шагам.

## Когда это нужно

`app.db` повреждена, потеряна, или нужно откатиться к состоянию до неудачной операции
(в т.ч. перед миграцией БД в Phase 3 — см. `RECONCILIATION/02_DATA_MIGRATION.md` §4).

## Предпосылки

- Есть файл бэкапа, снятый `scripts/backup-db.js` (или, до P0-05, старый ad-hoc снапшот —
  тогда шаг «проверка целостности» ниже особенно важен, такие снапшоты не гарантированно
  консистентны).
- **Процесс `irz-web-gpio` остановлен**, если восстанавливаете поверх живого пути
  (`pm2 stop irz-web-gpio`) — восстановление поверх файла, который активно пишет другой
  процесс, небезопасно независимо от самого restore-скрипта.

## Шаги

1. **Остановить процесс** (только если восстанавливаете в боевой путь, не в тестовый):
   ```
   pm2 stop irz-web-gpio
   ```
2. **Отвести в сторону текущий файл** (не удалять — на случай, если restore тоже пойдёт не так):
   ```
   mv /opt/irz-web/data/app.db /opt/irz-web/data/app.db.before-restore-$(date +%s)
   ```
3. **Восстановить**:
   ```
   node scripts/restore-db.js <файл-бэкапа> /opt/irz-web/data/app.db
   ```
   Скрипт сам откажется, если целевой путь уже существует (после шага 2 он не должен
   существовать) и сам откажется, если сам файл бэкапа повреждён (`quick_check`).
4. **Проверить вывод** — сверить количество строк по ключевым таблицам (`projects`, `users`,
   `modems`, `meters`, `readings`, ...) с тем, что ожидалось на момент снятия именно этого
   бэкапа. Явных «плохих» цифр (0 там, где заведомо не должно быть 0) быть не должно.
5. **Запустить процесс и проверить живьём**:
   ```
   pm2 start irz-web-gpio
   pm2 logs irz-web-gpio --lines 20 --nostream
   ```
   Убедиться, что запустился без ошибок, кабинет открывается, показания счётчиков видны.
6. Если всё в порядке — старый файл из шага 2 можно оставить ещё на какое-то время (не мешает,
   не в `data/` под тем же именем) и удалить позже вручную, когда уверенность в restore
   полная. Если что-то не так — можно откатиться назад тем же `mv` в обратную сторону.

## Что если сам restore не проходит quick_check

Значит и бэкап, и (возможно) все более старые бэкапы в retention-окне могут быть под вопросом —
это уже не про сам restore, а про то, что backup-процедуру (P0-05) нужно расследовать отдельно,
не пытаться форсировать восстановление заведомо битого файла.

## Проверено (P0-06, 2026-09-09)

Вся процедура прогнана целиком на синтетической тестовой БД в изолированном окружении, не на
проде и не на реальном `app.db` — см. отчёт по задаче. Живой прогон именно на VPS не входит в
рамки этой задачи (аналогично P0-05 — деплой требует отдельного разрешения).
