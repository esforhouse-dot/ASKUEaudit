## 4. Правила работы (нарушать нельзя)

1. **Ни одна задача не начинается без явной команды владельца** «Execute Task P3-01» /
   «Переходи к P3-01». Наличие утверждённого плана — не команда.
2. **Коммитить и пушить сразу после каждой задачи**, не дожидаясь отдельного «PASS» — ревью
   идёт по запушенному состоянию (прямое указание владельца 09.09.2026).
3. **`git add` только точечный, по именам файлов. Никогда `git add -A`** в этом репозитории —
   в рабочей копии могут лежать несвязанные правки владельца (см. §2.4).
4. **ADR-18:** нашёл конфликт между AUTHORITATIVE-решением и фактами — **не решать самому**:
   зафиксировать как `OPEN OWNER QUESTION` и остановиться по этому пункту (остальные, не
   связанные с конфликтом, можно продолжать).
5. **Ничего не деплоить и не рестартовать на VPS** без отдельного явного разрешения **на каждый
   такой шаг**.

**Чего Claude не трогает вообще:**

- Протокол Mercury/iRZ — `fetched/domains/metering/mercury*.js` — KEEP AS IS (ADR-02/05),

## 7. Деплой (когда владелец разрешит)

Git на сервере не используется. Деплой — одноразовым Python-скриптом (paramiko), который
пишется в корень папки, запускается `py deploy_*.py` и **удаляется сразу после**. Пароль
берётся у владельца в диалоге и не остаётся в скрипте дольше одного запуска.

| Локально | На сервере | Нужен `pm2 restart irz-web-gpio` |
|---|---|---|
| `fetched/server.js`, `db.js`, `auth.js`, `mailer.js`, `loginRateLimit.js` | `/opt/irz-web/*.js` | да |
| `fetched/domains/device/*.js`, `domains/metering/*.js` | `/opt/irz-web/domains/...` (проверить фактические пути на сервере — на VPS модули Меркурия исторически лежат в `/opt/irz-web/mercury/`) | да |
| `fetched/index.html`, `admin.html`, `login.html` | `/opt/irz-web/public/*.html` | нет (статика) |
| `fetched/scripts/*.js` | `/opt/irz-web/scripts/*.js` | нет |

`node --check <file>` **локально до отправки и на сервере после** — до рестарта. После рестарта:
`pm2 logs irz-web-gpio --lines 20 --nostream`.

**Грабли Windows:** временные файлы писать внутри папки проекта, не в `/tmp` (нативный Python
на Windows не понимает виртуальный `/tmp` из git-bash); кириллицу в `print()` кодировать
`.encode('ascii', errors='replace').decode('ascii')`, иначе `UnicodeEncodeError` (cp1251);
мусор в кириллице в выводе `curl`/`pm2` через консоль — артефакт кодировки, не порча данных.

## 9. Работа через GitHub (чтобы продолжать с любого устройства)

> Добавлено 15.10.2026 по просьбе владельца: «надо работать через GitHub, чтоб можно было всегда
> продолжить с другого устройства». Здесь — то, что реально проверено на этой машине, включая
> грабли, на которые уже наступили.

### 9.1. Три состояния кода, которые НЕ совпадают

Это главное, что надо понимать, садясь за проект на новом устройстве:

| Где | Что там | Как обновляется |
|---|---|---|
| **GitHub** (`esforhouse-dot/ASKUEaudit`) | то, что успели запушить | только `git push` |
| **Локальная папка** | канонический код (пути `fetched/domains/...`, обёртка `dUrl()` из P1-02) | работа Claude |
| **Прод** (`/opt/irz-web/` на VPS) | **адаптированная** версия: плоские пути `./mercury/`, без `dUrl()`, без `logAudit` | отдельный деплой-скрипт, см. §7 |

Прод намеренно отстаёт по архитектуре: рефакторинг Phase 0-2 туда не катали (ADR/план), поэтому
при деплое каждый раз накладывается точечный патч на СКАЧАННЫЙ с сервера файл, а не копируется
локальный. Не «синхронизировать» их бездумно — сломается.

### 9.2. Порядок работы

1. В начале сессии: `git fetch && git status` — убедиться, что локальное и `origin/main` сошлись.
2. Работа → `node --check` → деплой (с разрешения владельца, §7).
3. **Сразу после задачи — коммит и пуш** (правило §4 п.2). Точечный `git add <файлы>`,
   никогда `git add -A`: в рабочей копии бывают несвязанные правки владельца.
4. Что НЕ придёт с `git clone` и что надо донести отдельно — §2.1 (`CLAUDE.md`), §2.2 (память),
   §2.3 (ключи).

### 9.3. Грабли доступа к GitHub (все три пойманы живьём 15.10.2026)

При переносе папки целиком вместе с ней едет и `.git/config`, где могут остаться пути **старой**
машины. Симптомы и лечение:

| Ошибка | Причина | Лечение |
|---|---|---|
| `Identity file C:/Users/ДИР/.ssh/id_ed25519 not accessible` | в `.git/config` остался `core.sshCommand` с путями прошлой машины | `git config --unset core.sshCommand` (ключ и `known_hosts` лежат в стандартных местах, ssh найдёт сам). Чинить путь вручную плохо: в `C:/Users/ООО ДИР/` есть пробел и кириллица, и разбор строки ломается |
| `Host key verification failed` | в `~/.ssh/known_hosts` нет записи github.com | `ssh-keyscan -t ed25519 github.com`, **сверить отпечаток** с опубликованным GitHub (`SHA256:+DiY3wvvV6TuJJhbpZisF/zLDA0zPMSvHdkr4UvCOqU`) и дописать в `known_hosts`. Не добавлять вслепую |
| `Permission denied (publickey)` | ключ не привязан к аккаунту (см. §2.3 — лежал чужой `tract-deploy`) | **решено 15.10.2026: ушли с SSH на HTTPS + токен**, см. §9.4 |

Быстрая проверка доступа одной командой: `git ls-remote origin -h refs/heads/main` — отвечает
хешем, значит всё в порядке; падает — смотреть таблицу выше.

### 9.4. Как сейчас устроен доступ к GitHub (решение владельца 15.10.2026)

**SSH больше не используется** — remote переведён на HTTPS:

```
origin  https://github.com/esforhouse-dot/ASKUEaudit.git
```

Авторизация — **fine-grained Personal Access Token** (права: `Contents: Read and write`,
`Metadata: Read-only`, только репозиторий `ASKUEaudit`; срок — до 13.01.2027, дальше владелец
выпускает новый). Сам токен хранится в **Credential Manager Windows** (`credential.helper=manager`),
в файлы репозитория и в `.git/config` НЕ попадает — проверено.

Что это значит для новой машины:

1. `git clone https://github.com/esforhouse-dot/ASKUEaudit.git` — клон по HTTPS, без ключей.
2. При первом `git push` Credential Manager спросит логин/токен один раз и запомнит. Логин —
   `esforhouse-dot`, пароль — **токен**, не пароль от аккаунта GitHub (он не подойдёт).
3. Claude сам токен не придумает и из памяти не достанет — **спрашивать у владельца**, как и
   пароль от VPS (§2.3, P0-01).
4. Если push начал падать с `403` / `Authentication failed` — скорее всего истёк срок токена:
   владелец выпускает новый на https://github.com/settings/personal-access-tokens, после чего
   сохранить его командой (токен подставить, в файлы не писать):

```bash
printf 'protocol=https\nhost=github.com\nusername=esforhouse-dot\npassword=<ТОКЕН>\n\n' | git credential approve
```
