## P1-01 — Извлечь `modemState.js` + GPIO-маршруты в `domains/device/`

**Phase:** 1

**Цель:** Физический перенос кода в `fetched/domains/device/` без изменения логики/поведения —
первый шаг strangler-извлечения `server.js` (ADR-03).

**Файлы/модули:** `fetched/modemState.js` → `fetched/domains/device/modemState.js`; GPIO-маршруты
из `fetched/server.js` (`/api/gpo/*`, `/api/pin/*`, `/api/info`, `/api/ussd`,
`server.js:2489-2578`, `2754-2766`) → `fetched/domains/device/routes.js`; `server.js` обновляется
только для подключения (`require`/mount), не более.

**Зависимости:** все `P0-*`.

**Разрешено менять:** пути `require()`, расположение файлов, монтирование маршрутов в
`server.js` (замена инлайновых определений на `app.use(deviceRoutes)` или эквивалент).

**Запрещено менять:** любую логику внутри перенесённых функций — валидацию GPIO-пинов, формат
USSD-команд, работу очередей `serializeFor`/`serializeGpioFor`, обработку ошибок. Если при
переносе возникает соблазн «заодно улучшить» — не делать в рамках этой задачи (отдельная
задача, отдельное решение).

**Acceptance criteria:** идентичное поведение до/после — те же HTTP-ответы на те же запросы, то
же физическое поведение GPIO/USSD. Diff показывает перемещение кода и правку путей импорта, не
изменение логики.

**Tests/regression checks:** формального regression-набора для этого домена ещё нет
(`AUDIT/12_TECH_DEBT.md` #2) — для этой задачи минимально необходимо: (1) smoke-тест,
покрывающий каждый перенесённый маршрут (может быть написан как часть этой задачи — хорошая
точка старта для будущего regression-harness, но не блокирует задачу, если пишется как ручной
чек-лист); (2) построчное сравнение перенесённого кода со старым (diff должен показывать 0 строк
логики, изменённых по существу).

**Staging verification:** полный прогон GPIO (вкл/выкл нагрузки, направление/уровень пина 1-3,
VCC4, USSD, чтение ICCID/LBS) на staging-копии с реальным подключённым модемом (если доступен в
staging) или задокументированной симуляцией.

**Production verification:** после деплоя — тот же прогон на реальном модеме одного проекта;
`pm2 logs irz-web-gpio` без новых ошибок в первые минуты после рестарта.

**Rollback plan:** `git revert` коммита переноса, передеплой предыдущей версии `server.js` +
удаление `domains/device/` (или просто не подключать).

**Risk:** LOW-MEDIUM. Технически простой перенос, но единственная защита от регрессии —
ручная/staging проверка (нет автотестов) — внимательность при diff-ревью обязательна.

## P1-02 — N модемов на объект (снять `LIMIT 1`, добавить `?modemId=`)

**Phase:** 1 (ADR-14, owner decision 2026-09-09)

**Цель:** Реализовать целевую модель Organization→Objects→**Modems**→RS-485→Meters на уровне
Device Core — один проект/объект может иметь несколько активных модемов.

**Файлы/модули:** `fetched/server.js` (middleware `server.js:1240-1249`, резолвящий
`req.modem`/`req.meter` — убрать `LIMIT 1`, добавить чтение `?modemId=` по аналогии с уже
существующим `?meterId=`); `fetched/index.html` (UI-селектор активного модема, по образцу уже
существующего селектора счётчика).

**Зависимости:** все `P0-*`; логически удобнее исполнять после `P1-01` (домен Device Core уже
вынесен в отдельное место), но не жёсткая техническая зависимость.

**Разрешено менять:** middleware резолюции `req.modem` (переход от `LIMIT 1` к
списку+выбору), добавление UI-компонента выбора модема.

**Запрещено менять:** сам паттерн tenant-isolation (`WHERE project_id = ?`) — модемы по-прежнему
жёстко скоупятся к `req.projectId`, просто из «ровно один» в «один из списка, явно выбранный».
Не трогать логику резолюции `req.meter` (`WHERE modem_id = ?`) — она уже корректна и должна
продолжать работать per-modem без изменений.

**Acceptance criteria:** (1) существующие проекты с одним модемом продолжают работать
**без каких-либо видимых изменений** (модем выбирается по умолчанию, как раньше); (2) проект с
2+ модемами показывает селектор, переключение модема корректно меняет отображаемые
счётчики/GPIO-статус; (3) **попытка обратиться к модему, не принадлежащему `req.projectId`,
через `?modemId=` даёт тот же результат, что и сегодня для `?meterId=` — пустой/404, не чужие
данные** (это самый чувствительный критерий приёмки для этой задачи).

**Tests/regression checks:** staging-тест с синтетическим проектом, имеющим 2 модема — проверка
переключения; отдельный security-тест — подстановка `modemId` чужого проекта в запрос,
подтверждение отказа (аналогично тому, как это уже проверено для `meterId` в
`AUDIT/09_AUTH_AND_SECURITY.md`).

**Staging verification:** создать тестовый проект с 2 модемами на staging, пройти полный цикл
(выбор модема → просмотр счётчиков → GPIO-статус → переключение на второй модем → повтор).

**Production verification:** точечная проверка на реальном проекте (если есть с 2+ модемами)
или контролируемое создание тестового; подтверждение, что однмодемные проекты не заметили
изменений.

**Rollback plan:** `git revert`, передеплой предыдущей версии `server.js`/`index.html`.

**Risk:** **MEDIUM** — это изменение затрагивает middleware, который `AUDIT/09_AUTH_AND_SECURITY.md`
отдельно отметил как один из немногих компонентов без замечаний по безопасности (корректная
tenant isolation). Ошибка здесь — потенциальная утечка данных между тенантами, самый серьёзный
класс риска в этом плане. Требует более тщательного ревью диффа и staging-теста, чем большинство
других задач Phase 1.

## P1-03 — MySQL-пул: добавить `connectTimeout`

**Phase:** 1

**Цель:** Закрыть остаточный риск исчерпания пула `irzserver4` без ограничения по времени
(`AUDIT/06_IRZ_MODEMS.md` — таймаут-гвард в `serializeGpioFor` уже смягчает симптом, но не
первопричину).

**Файлы/модули:** `fetched/server.js` (`mysql.createPool(...)`, `server.js:146-147`) — добавить
`connectTimeout` (и/или явную стратегию восстановления пула).

**Зависимости:** все `P0-*`.

**Разрешено менять:** только параметры конфигурации `createPool` — не сам код запросов к пулу.

**Запрещено менять:** `connectionLimit`, логику запросов, `serializeGpioFor` (тот уже содержит
свой независимый таймаут-гвард — эта задача не заменяет его, а закрывает первопричину рядом).

**Acceptance criteria:** при недоступности/исчерпании пула запрос на получение соединения
отказывает в пределах заданного таймаута, не висит неограниченно.

**Tests/regression checks:** на staging — намеренно исчерпать пул (открыть `connectionLimit`
параллельных соединений искусственно) и подтвердить, что следующий запрос завершается ошибкой
в пределах таймаута, а не висит.

**Staging verification:** тест исчерпания пула, как описано выше.

**Production verification:** мониторинг `pm2 logs` после деплоя на предмет изменений в
поведении GPIO-канала; отсутствие новых зависаний.

**Rollback plan:** откат значения конфигурации.

**Risk:** LOW — небольшое, локализованное изменение конфигурации.
