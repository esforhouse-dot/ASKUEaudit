## P0-01 — Убрать секреты из `CLAUDE.md`

**Phase:** 0 (workstream A, ADR-08)

**Цель:** `CLAUDE.md` перестаёт содержать значения секретов (пароль root VPS по SSH, пароль
почты, пароль SMTP-приложения) в открытом виде — только указание, где их искать теперь.

**Файлы/модули:** `CLAUDE.md` (правка текста). Новое место хранения секретов — **вне
репозитория** (менеджер паролей/зашифрованное хранилище — конкретный инструмент выбирает
владелец, это не техническое решение Claude Code).

**Зависимости:** нет — может исполняться первой.

**Разрешено менять:** только текст `CLAUDE.md` (удалить литеральные значения, заменить на
описание нового места хранения).

**Запрещено менять:** любые файлы `fetched/*`, любые production-файлы на VPS, сами секреты на
сервере (`/root/.irz_*_password` — те уже правильно хранятся вне репозитория, не трогаются
этой задачей).

**Acceptance criteria:** grep по `CLAUDE.md` на известные секретные значения даёт 0 совпадений;
владелец подтвердил, что секреты сохранены в новом месте и доступны.

**Tests/regression checks:** `grep` (или аналог) по репозиторию на три конкретных строки-секрета
— 0 файлов с совпадением, включая сам `CLAUDE.md`.

**Staging verification:** не применимо (правка документации, не кода).

**Production verification:** не применимо (не затрагивает `fetched/`/VPS).

**Rollback plan:** `git revert` одного коммита — тривиально, `CLAUDE.md` не влияет на
работающее приложение.

**Risk:** LOW. Единственный практический риск — потерять доступ к секретам, если новое место
хранения не подтверждено владельцем ДО удаления из `CLAUDE.md` — задача не считается
завершённой без этого подтверждения.

## P0-02 — Ротация скомпрометированных credentials

**Phase:** 0 (workstream A, ADR-08)

**Цель:** Сменить пароль root VPS по SSH, пароль почтового ящика `irz_dir2@mail.ru`, пароль
SMTP-приложения — независимо от того, что они не найдены в git-истории (см.
`RECONCILIATION/04_RISK_REGISTER.md` R-13) — сам факт долгого хранения в открытом виде на диске
не даёт полной гарантии.

**Файлы/модули:** `/root/.irz_smtp_password` на VPS (обновляется новым значением). Пароль VPS
root и пароль почты — не файлы в репозитории, меняются напрямую (SSH/панель mail.ru).
`DB_PASSWORD`/`WEB_PASSWORD` (`/root/.irz_db_password`, `/root/.irz_web_password`) **НЕ входят**
в эту задачу — они не были обнаружены в открытом виде, ротация не требуется этим решением.

**Зависимости:** P0-01 (новое место хранения секретов должно существовать до ротации, иначе
новый пароль негде безопасно записать).

**Разрешено менять:** пароль VPS root, пароль почтового ящика, содержимое
`/root/.irz_smtp_password`.

**Запрещено менять:** `DB_PASSWORD`/`WEB_PASSWORD` и их файлы, любой код `fetched/*`, конфигурацию
`irzserver4`/MySQL.

**Acceptance criteria:** старые значения всех трёх credentials больше не работают; новые
работают; `irz-web-gpio` после рестарта успешно логинится в SMTP (это уже проверяется кодом
при каждом старте — `mailer.verifyTransport()`, `server.js:2775-2777`).

**Tests/regression checks:** ручной SSH-логин новым паролем; ручной вход в почту новым паролем;
после обновления `/root/.irz_smtp_password` и `pm2 restart irz-web-gpio` — `pm2 logs
irz-web-gpio --lines 20` показывает `✅ SMTP (irz_dir2@mail.ru) готов к отправке`, не ошибку.

**Staging verification:** не применимо напрямую (это ротация инфраструктурных credentials, не
код) — но SMTP-часть можно проверить локальным тестовым скриптом с новым паролем ДО замены
файла на проде.

**Production verification:** `pm2 logs irz-web-gpio` после рестарта — успешный SMTP-логин;
следующий реальный алерт/отчёт по email доставляется.

**Rollback plan:** вернуть старое значение в `/root/.irz_smtp_password` + `pm2 restart` — если
новый пароль почему-то не проходит. Для SSH/почты — у владельца должен быть способ восстановить
доступ (у большинства провайдеров — через панель управления/резервный email), не через сам SSH.

**Risk:** **MEDIUM.** Ошибка при смене пароля VPS root по SSH рискует потерей доступа к серверу,
если не сохранён альтернативный путь входа (например, через панель хостинга) до завершения
смены. Ошибка в `/root/.irz_smtp_password` временно ломает исходящую почту (алерты/отчёты) —
не критично мгновенно, но требует быстрого исправления. Эта задача требует прямого участия
владельца в момент исполнения (не полностью автономна), в отличие от большинства остальных
задач Phase 0.

## P0-03 — Rate-limiting на `/api/login`

**Phase:** 0 (workstream A, ADR-08)

**Цель:** Ограничить число неудачных попыток входа по IP+логину, закрыть риск R-02.

**Файлы/модули:** `fetched/server.js` (маршрут `POST /api/login`, `server.js:921-942`) — точечно
вокруг этого маршрута, либо новый небольшой модуль `fetched/rateLimit.js`.

**Зависимости:** нет.

**Разрешено менять:** только код вокруг `/api/login` (добавление счётчика попыток/блокировки).

**Запрещено менять:** `auth.js` (механизм сессий/bcrypt не трогается), любые другие маршруты.

**Acceptance criteria:** N неудачных попыток за окно времени (например, 5 за 15 минут на
IP+логин) → следующая попытка отклоняется без обращения к bcrypt; корректный логин после
паузы/с корректным паролем по-прежнему проходит.

**Tests/regression checks:** скриптовый прогон N+1 заведомо неверных попыток → подтвердить
блокировку N+1-й; отдельный тест — верный пароль в пределах лимита проходит нормально.

**Staging verification:** прогон того же скрипта на staging-копии перед деплоем в прод.

**Production verification:** ручная проверка — несколько намеренно неверных попыток с тестового
аккаунта, подтвердить блокировку; подтвердить, что реальный логин не пострадал.

**Rollback plan:** `git revert`, передеплой предыдущей версии `server.js`.

**Risk:** LOW-MEDIUM. Слишком агрессивный порог может заблокировать легитимного пользователя,
опечатавшегося несколько раз подряд — выбрать разумный порог (не 2-3 попытки), тестировать на
staging перед продом.

## P0-04 — Security headers в nginx (CSP/HSTS/Referrer-Policy)

**Phase:** 0 (workstream A, ADR-08)

**Файлы/модули:** `fetched/nginx-askue.conf` + фактический конфиг на VPS.

**Зависимости:** нет.

**Разрешено менять:** только `add_header`-директивы, добавляемые к уже существующим
(`X-Frame-Options`/`X-Content-Type-Options` уже есть, не трогать).

**Запрещено менять:** `proxy_pass`, SSL-конфигурацию, любые другие server-блоки на VPS
(в частности — конфиги `irz-modem-control`, `space-cakes`, `video-worker`, если они на том же
nginx).

**Acceptance criteria:** ответ сервера содержит `Content-Security-Policy`,
`Strict-Transport-Security`, `Referrer-Policy`; приложение продолжает полностью работать.

**Tests/regression checks:** `curl -I` подтверждает заголовки; ручной прогон всех разделов
`index.html`/`admin.html` в браузере — 0 CSP-нарушений в консоли. **Важный нюанс, обязательный
к учёту при формулировке CSP:** фронтенд активно использует инлайновые `<script>`/`<style>`
(`AUDIT/04_FRONTEND.md`) — CSP без `'unsafe-inline'` (или без nonce-механизма) сломает
приложение целиком. Задача НЕ считается выполненной, если после включения CSP приложение
перестаёт работать — это не приемлемый компромисс ради формального заголовка.

**Staging verification:** применить конфиг на staging nginx-блоке (или тестовый reload) перед
продовым `nginx -s reload`.

**Production verification:** `curl -I https://askue.o-dir.ru`, ручной прогон интерфейса.

**Rollback plan:** восстановить предыдущий `nginx-askue.conf`, `nginx -s reload` — секунды,
без даунтайма самого Node-процесса.

**Risk:** LOW технически, но **конкретный риск — сломать инлайн-скрипты неверной CSP**
(см. выше). Проверка в браузере обязательна, не полагаться только на `curl`.

## P0-05 — Автоматический бэкап `app.db`

**Phase:** 0 (workstream D, ADR-10)

**Цель:** Регулярный (минимум ежедневный) бэкап + retention-политика, закрыть R-14.

**Файлы/модули:** новый скрипт (например, `fetched/scripts/backup-db.js` или shell-скрипт) +
cron-задача на VPS. Использует безопасное копирование SQLite (WAL-checkpoint + копия файла, или
встроенный `.backup` — не читает `app.db` напрямую во время записи).

**Зависимости:** нет технической, но **логически предшествует** P0-06 (нечего восстанавливать
без бэкапа) и является жёсткой предпосылкой для Phase 3 (миграция БД без бэкапа запрещена).

**Разрешено менять:** добавление нового скрипта + cron-записи. Не изменяет `app.db` — только
читает.

**Запрещено менять:** сам `irz-web-gpio` процесс, схему БД, любой код `fetched/*.js` кроме
нового скрипта.

**Acceptance criteria:** бэкап создаётся автоматически по расписанию; хранится **вне** диска
production-VPS (см. риск R-16 — существующие ad-hoc бэкапы сейчас на том же диске); действует
retention (старые бэкапы не накапливаются бесконечно).

**Tests/regression checks:** ручной запуск скрипта — файл создан, открывается `sqlite3`,
количество строк в ключевых таблицах совпадает с живой БД на момент снятия.

**Staging verification:** прогон скрипта против копии `app.db` на staging до включения в
продовый cron.

**Production verification:** после первого планового запуска — подтвердить наличие свежего
бэкапа вне production-диска с корректным размером/контрольной суммой.

**Rollback plan:** удаление cron-записи — не влияет на работающий процесс `irz-web-gpio`.

**Risk:** LOW для самого приложения (read-only копирование). **Открытый момент, требующий
решения владельца до полного исполнения:** конкретное место хранения off-server бэкапов не
определено ни в `AUDIT/*`, ни в `RECONCILIATION/*` — это не конфликт с утверждённым решением
(ADR-18 неприменим), а недостающая деталь, которую нужно получить от владельца перед началом
(например: другой VPS? облачное хранилище? — выбор инструмента вне компетенции этой задачи).

## P0-07 — Расследование 140 pm2-рестартов `irz-web-gpio`

**Phase:** 0 (workstream D, ADR-11)

**Цель:** Установить причину каждой категории рестартов за доступное окно логов; устранить
корневую причину там, где это возможно в рамках малой правки.

**Файлы/модули:** нет правки кода на первом шаге — анализ `pm2 logs irz-web-gpio` (максимально
доступная глубина), `pm2 jlist` (счётчики). Если находится конкретная устранимая причина —
точечная правка (аналогично уже сделанным фиксам таймаутов в `modemState.js`) оформляется как
**отдельная follow-up задача**, не смешивается с самим расследованием.

**Зависимости:** нет.

**Разрешено менять:** для самого расследования — ничего (read-only). Follow-up фикс (если
найден) — только тот конкретный файл/участок, где установлена причина.

**Запрещено менять:** ничего без установленной причины — не чинить наугад (прямое указание
владельца при постановке этой задачи).

**Acceptance criteria:** каждый рестарт в доступном окне логов отнесён к одной из категорий
(crash / OOM / uncaught exception / ручной рестарт / деплой / watchdog / сеть-железо); для
доминирующей категории — установлена конкретная причина, не предположение. Если причина не
устанавливается однозначно по доступным логам — фиксируется явно, не заполняется догадкой.

**Tests/regression checks:** не применимо к самому расследованию. Если есть follow-up фикс — тот
получает собственные tests/regression checks в своей отдельной задаче.

**Staging verification / Production verification:** не применимо к расследованию.

**Rollback plan:** не применимо — расследование ничего не меняет.

**Risk:** LOW для самого расследования (чтение логов). Риск в том, что часть истории логов уже
может быть недоступна (ротация логов pm2) — если так, это фиксируется как ограничение
результата, не блокер задачи.

появилась; `pm2 logs` не показывает новых ошибок после деплоя.

удаляется отдельным шагом при желании.

**Risk:** LOW — аддитивное изменение (новая таблица + необязательная побочная запись), не
меняет существующее поведение API при корректной реализации (try/catch вокруг записи лога —
обязательное условие acceptance).

**Разрешено менять:** добавление staging-механизма (не подменяющего существующий деплой-процесс

**Запрещено менять:** сам механизм деплоя на прод (`paramiko`-скрипты остаются как есть).

**Acceptance criteria:** документированная, повторяемая процедура staging-проверки существует и
была использована хотя бы один раз на реальном (пусть небольшом) изменении до его деплоя в прод.

**Tests/regression checks:** сам факт успешного прохождения хотя бы одного изменения через
staging → verify → prod — это и есть проверка работоспособности процесса.

**Staging/Production verification:** эта задача сама создаёт механизм verification для всех
последующих задач — предметно проверяется однократным использованием.

**Rollback plan:** не применимо — аддитивный процесс, не заменяет существующий.

**Risk:** LOW, но **наименее конкретизированная задача Phase 0** — точная форма staging
(второй процесс? отдельный VPS? локальное окружение?) требует решения владельца перед полным
исполнением, не изобретается Claude Code самостоятельно (согласно принципу мастер-промпта «не
выдумывать» и правилу ADR-18 — это скорее недостающая деталь, чем конфликт, но требует того же
типа паузы для уточнения).
