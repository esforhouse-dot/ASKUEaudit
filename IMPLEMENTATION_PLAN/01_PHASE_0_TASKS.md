## P0-02 — Ротация скомпрометированных credentials

> **Статус (2026-09-09): `DEFERRED / ACCEPTED OWNER RISK`.** Прерогатива закрытия при этом
> статусе — см. `00_OVERVIEW_AND_GOVERNANCE.md`, «Статусы закрытия задачи». Ниже — фактический
> исход исполнения, зафиксированный как есть, не как незакрытая техническая ошибка.
>
> **Что сделано:** независимый от пароля SSH-доступ к VPS создан и живьём проверен (отдельный
> ключ `id_ed25519_vps`, подтверждён вход с `PasswordAuthentication=no`) — предусловие ниже
> выполнено технически. Заодно обнаружен и владельцем подтверждён как легитимный уже
> существовавший в `authorized_keys` ключ `tract-deploy` и вход с IP `95.139.45.29` — оба
> принадлежат владельцу, ложной тревоги не было.
>
> **Что НЕ сделано и почему:** сама смена трёх паролей (VPS root SSH, почта `irz_dir2@mail.ru`,
> SMTP-приложение) не выполнена. **Владелец явно решил отложить** — на этом же VPS завязаны
> другие production-проекты и агенты, не относящиеся к АСКУЭ (`space-cakes`, `video-worker` и,
> возможно, другие — см. `tract-deploy` выше), и владелец не хочет менять общие для VPS
> credentials вне отдельного, спланированного окна обслуживания, где можно проверить последствия
> для всех зависимых систем разом, а не только для `irz-web-gpio`. Дополнительно владелец явно
> оценил риск раскрытия текущих значений (видны только ему и Claude в рамках этой сессии) как
> приемлемый на данный момент.
>
> **Обязательство, которое это НЕ отменяет:** ротация остаётся нужной и запланированной — просто
> не сейчас. См. обновлённый `RECONCILIATION/04_RISK_REGISTER.md` R-01 — риск остаётся открытым
> (не закрытым) до фактической ротации, привязки к конкретной дате нет, инициатива — за
> владельцем.

**Phase:** 0 (workstream A, ADR-08)

**Цель:** Сменить пароль root VPS по SSH, пароль почтового ящика `irz_dir2@mail.ru`, пароль
SMTP-приложения — независимо от того, что они не найдены в git-истории (см.
`RECONCILIATION/04_RISK_REGISTER.md` R-13) — сам факт долгого хранения в открытом виде на диске
не даёт полной гарантии.

**Файлы/модули:** `/root/.irz_smtp_password` на VPS (обновляется новым значением). Пароль VPS
root и пароль почты — не файлы в репозитории, меняются напрямую (SSH/панель mail.ru).
`DB_PASSWORD`/`WEB_PASSWORD` (`/root/.irz_db_password`, `/root/.irz_web_password`) **НЕ входят**
в эту задачу — они не были обнаружены в открытом виде, ротация не требуется этим решением.

**Зависимости:** P0-01 (новое место хранения секретов должно существовать до ротации, иначе
новый пароль негде безопасно записать).

**Обязательное предварительное условие (правка 2026-09-09) — до смены пароля root VPS по SSH:**
подтвердить и живьём проверить рабочий **альтернативный доступ к VPS**, независимый от текущего
SSH-пароля (например: web-консоль/VNC хостинг-провайдера, recovery-режим, второй
существующий SSH-ключ/аккаунт). Смена пароля root **не начинается**, пока этот альтернативный
путь не проверен работающим — иначе единственный способ восстановиться после неудачной смены
пароля — это сам скомпрометированный пароль, что обнуляет смысл ротации.

**Разрешено менять:** пароль VPS root, пароль почтового ящика, содержимое
`/root/.irz_smtp_password`.

**Запрещено менять:** `DB_PASSWORD`/`WEB_PASSWORD` и их файлы, любой код `fetched/*`, конфигурацию
`irzserver4`/MySQL.

**Acceptance criteria:** старые значения всех трёх credentials больше не работают; новые
работают; `irz-web-gpio` после рестарта успешно логинится в SMTP (это уже проверяется кодом
при каждом старте — `mailer.verifyTransport()`, `server.js:2775-2777`).

**Tests/regression checks:** ручной SSH-логин новым паролем; ручной вход в почту новым паролем;
после обновления `/root/.irz_smtp_password` и `pm2 restart irz-web-gpio` — `pm2 logs
irz-web-gpio --lines 20` показывает `✅ SMTP (irz_dir2@mail.ru) готов к отправке`, не ошибку.

**Staging verification:** не применимо напрямую (это ротация инфраструктурных credentials, не
код) — но SMTP-часть можно проверить локальным тестовым скриптом с новым паролем ДО замены
файла на проде.

**Production verification:** `pm2 logs irz-web-gpio` после рестарта — успешный SMTP-логин;
следующий реальный алерт/отчёт по email доставляется.

**Rollback plan (правка 2026-09-09 — НЕ откатываться к скомпрометированному значению):** если
новое значение по какой-то причине не работает — не возвращать старый (уже признанный
скомпрометированным) пароль ни для одного из трёх credentials. Вместо этого: через уже
проверенный альтернативный доступ (см. предварительное условие выше) установить **ещё одно
новое** значение. Единственное исключение — `/root/.irz_smtp_password`: если новый SMTP-пароль
не проходит проверку `mailer.verifyTransport()`, допустимо временно отключить/пропустить
исходящую почту (деградация функциональности, не угроза доступа) на время генерации следующего
нового значения — но не возвращать старый файл как постоянное решение.

**Risk:** **MEDIUM.** Ошибка при смене пароля VPS root по SSH рискует потерей доступа к серверу
— смягчается обязательной проверкой альтернативного доступа ДО начала смены (см. выше), не
ротацией привычки «есть старый пароль про запас». Ошибка в `/root/.irz_smtp_password` временно
ломает исходящую почту (алерты/отчёты) — не критично мгновенно, но требует быстрого исправления
без отката к скомпрометированному значению. Эта задача требует прямого участия владельца в
момент исполнения (не полностью автономна), в отличие от большинства остальных задач Phase 0.

опечатавшегося несколько раз подряд — выбрать разумный порог (не 2-3 попытки), тестировать на
staging перед продом.

## P0-05 — Автоматический бэкап `app.db`

> **Статус (2026-09-09, PASS владельца на реализацию):**
> - **app.db backup implementation — `PASS`.** Код принят, ничего в нём переделывать не нужно.
> - **Local backup (заглушка `ASKUE_BACKUP_DIR` внутри `data/`) — только временный
>   fallback/test-режим.** Не production-конфигурация ни при каких условиях — существует
>   исключительно чтобы скрипт был runnable/тестируемым до выбора реального места.
> - **Production cron — пока НЕ устанавливать.** Ни на каком основании, включая «код же
>   готов» — установка ждёт отдельного явного разрешения владельца, отдельно от PASS на код.
> - **Off-server storage — `OPEN OWNER DECISION`.** Куда физически писать бэкапы — решает
>   владелец, не Claude Code; без этого решения задача не может перейти в полное `DONE`.
> - **Risk R-16 (`RECONCILIATION/04_RISK_REGISTER.md`) остаётся открытым**, пока storage не
>   выбран и cron не установлен — реализация скрипта сама по себе R-16 не закрывает.
>
> Новый `fetched/scripts/backup-db.js` —
> `better-sqlite3` `db.backup()` (штатный API, не файловая копия), quick_check-верификация
> каждого снятого бэкапа, retention 14 дней, каталог назначения — через `ASKUE_BACKUP_DIR`
> (по умолчанию заглушка внутри `data/`, специально НЕ off-server — см. блокер ниже).
>
> Проверено на синтетической БД (5/500 строк в двух таблицах, WAL-режим) в изолированном
> тестовом окружении, ничего в `fetched/` не создавалось: 3 последовательных прогона —
> счётчики строк в бэкапе точно совпадают с источником, `quick_check=ok`. **Живым тестом
> найден и исправлен реальный баг**: точность имени файла до секунды приводила к тому, что два
> быстрых подряд запуска получали одинаковое имя и второй молча ЗАТИРАЛ бэкап первого через тот
> же `db.backup()` — можно было бы потерять единственный на тот момент бэкап, ничего об этом не
> узнав. Исправлено на миллисекундную точность, тем же тестом подтверждено: второй прогон создаёт
> отдельный файл, retention корректно вычищает только состарившиеся.
>
> **`OPEN OWNER QUESTION` (жёсткое предусловие из этой же карточки, ещё не снято):** куда физически
> писать off-server бэкапы — не решено. Пока `ASKUE_BACKUP_DIR` не указывает на подтверждённое
> off-server место, cron-задачу на VPS ставить нельзя (иначе бэкап остаётся на том же диске, что
> и сам `app.db` — риск R-16 не закрывается). Как только место определено — установка cron
> тривиальна, сам скрипт готов.

**Phase:** 0 (workstream D, ADR-10)

**Цель:** Регулярный (минимум ежедневный) бэкап + retention-политика, закрыть R-14.

**Файлы/модули:** новый скрипт (например, `fetched/scripts/backup-db.js`) + cron-задача на VPS.

**Механизм (уточнено 2026-09-09) — обязательно через штатный SQLite backup API, не файловую
копию:** прямое копирование файла активной WAL-режима БД (даже «только на чтение» —
`cp`/`fs.copyFile`) **не гарантирует консистентность** — можно скопировать файл в момент, когда
часть изменений ещё в WAL, а не в основном файле, и получить повреждённый или рассинхронизированный
бэкап. Использовать один из штатных механизмов SQLite, спроектированных для копирования
активной БД без остановки писателя: (а) команда `sqlite3 app.db ".backup '<путь>'"`, либо
(б) `better-sqlite3`-метод `db.backup(destinationPath)` (тот же движок, что уже использует
приложение — предпочтительно, не требует внешнего бинаря `sqlite3` на сервере). Любой другой
способ (сырое копирование файла, `tar` активной директории `data/`) не допускается.

**Обязательное предусловие до исполнения (жёсткое, не заметка на будущее):** off-server

предшествует P0-06 (нечего восстанавливать без бэкапа) и является жёсткой предпосылкой для

**Acceptance criteria:** бэкап создаётся автоматически по расписанию; хранится **вне** диска

## P0-09 — `audit_logs` + логирование критических действий

**Phase:** 0 (ADR-12)

**Цель:** Ввести единый журнал критических действий заранее, не откладывая до Partner Network.

**Файлы/модули:** `fetched/db.js` (новая таблица `audit_logs`), `fetched/server.js` (точечное
добавление вызовов логирования в конкретных маршрутах): смена тарифа
(`/api/site/tariff` POST/DELETE), удаление счётчика (`DELETE /api/meters/:id`), удаление модема
(`DELETE /api/modems/:id`), impersonation (`/api/admin/impersonate/:projectId`,
`/api/admin/stop-impersonate`), сброс пароля пользователя
(`/api/admin/users/:id/reset-password`).

**Зависимости:** нет.

**Разрешено менять:** добавление таблицы; добавление вызова записи лога **рядом** с уже
существующей логикой перечисленных маршрутов.

**Запрещено менять:** саму бизнес-логику этих маршрутов — только добавляется побочная запись в
`audit_logs`, поведение ответа API не меняется. Запись в лог не должна быть блокирующей для

аудите: журнал выглядит полным, но часть событий физически отсутствует, и никто об этом не
узнает. Try/catch решает проблему «не уронить основной запрос», но не заменяет наблюдаемость
самого сбоя логирования.

actor, действием, целью, временем; при смоделированном сбое записи (например, временно
недоступная БД) — основной запрос всё равно завершается успешно, **и** в `pm2 logs` появляется
явная ошибка о несостоявшейся записи аудита с указанием, какое именно действие не залогировано.

**Tests/regression checks:** для каждого из 5 перечисленных маршрутов — вызвать на staging,
подтвердить появление соответствующей строки в `audit_logs` с корректными полями; отдельно —
смоделировать сбой записи (например, временно запретить запись в таблицу) и подтвердить, что
ошибка видна в логах процесса, а не проглатывается молча.

**Staging verification:** полный прогон всех 5 маршрутов на staging-копии.

**Production verification:** точечная проверка 1-2 реальных действий после деплоя — строка
появилась; `pm2 logs` не показывает новых ошибок после деплоя.

**Rollback plan:** `git revert` — таблица может остаться в БД неиспользуемой (не мешает), либо
удаляется отдельным шагом при желании.

**Risk:** LOW — аддитивное изменение (новая таблица + побочная запись), не меняет существующее
поведение API при корректной реализации. Конкретный риск, если сделать небрежно: try/catch без
логирования самой ошибки превращает `audit_logs` в источник ложной уверенности («аудит есть»,
хотя часть событий тихо потеряна) — именно поэтому наблюдаемость сбоя записи включена в
acceptance criteria, а не оставлена на усмотрение реализации.
