# DEPLOYMENT LIFECYCLE (P0-10)

> Реализует `RECONCILIATION/03_IMPLEMENTATION_SEQUENCE.md` §0 (`Git → review → staging/test →
> production → monitoring/backup → rollback`) конкретными, проверенными шагами — не абстрактной
> схемой. Задача помечена в карточке как «наименее конкретизированная задача Phase 0» — этот
> документ закрывает то, что можно закрыть без решения владельца (методику + процедуру), и явно
> называет то, что решения владельца ждёт (провижининг на VPS), не изобретая его самостоятельно.

## Два уровня проверки — не один абстрактный «staging»

### Уровень 1 — Изолированная проверка логики (работает уже сегодня, VPS не нужен)

**Для чего:** любая логика, не требующая полного рантайма `server.js` (MySQL-пул, Java-демон,
живая шина Mercury) — чистые функции, схема БД, отдельные модули.

**Механизм:** копия проверяемого файла (или файлов) в изолированный каталог вне `fetched/`, с
собственной установкой зависимости (`better-sqlite3` и т.п.), прогон против синтетических/
одноразовых данных, включая намеренный инжект отказа там, где это уместно (сбой записи, битый
файл и т.п.). Ничего в `fetched/` не создаётся и не меняется в процессе проверки.

**Это не гипотеза — уже 4 раза реально сработало в этой же фазе, каждый раз находя настоящую
проблему до коммита, не после:**

| Задача | Что проверялось | Что нашлось |
|---|---|---|
| P0-03 | `loginRateLimit.js` в изоляции, 17 проверок | `checkAllowed()` создавал запись в Map при простом чтении — атакующий мог раздувать память без единой неудачной попытки |
| P0-05 | `backup-db.js` против синтетической БД, 3 прогона подряд | Точность имени файла до секунды — два быстрых прогона подряд молча затирали бэкап друг друга |
| P0-06 | `restore-db.js`, сквозной цикл backup→restore + 2 сценария отказа | Не-SQLite файл ронял `quick_check` необработанным исключением — пользователь увидел бы сырой стектрейс вместо понятного сообщения |
| P0-09 | `logAudit()` (копия функции дословно) против копии `db.js`, 7 вызовов + сбой записи | Подтверждено (не найдено новых проблем) — сбой записи корректно не теряется молча |

Это и есть работающий Tier-1 staging-механизм для изменений, скоуп которых — один модуль/файл:
не аспирационный, а тот, что уже 4 раза ловил реальные баги до продакшена.

### Уровень 2 — Полный HTTP/интеграционный staging (спроектирован, не запущен — ждёт разрешения)

**Для чего:** изменения, которым нужен весь рантайм `server.js` целиком (новые маршруты,
правки middleware, затрагивающие весь конвейер запроса, что угодно, завязанное на реальную
интеграцию MySQL/Java-демон/шину Mercury).

**Почему Уровня 1 для этого недостаточно — установлено эмпирически в этой же фазе, не
предположение:** `server.js` физически не запускается вне VPS. Жёсткие зависимости:
`/root/.irz_db_password`/`/root/.irz_web_password` (абсолютные Linux-пути), MySQL-пул к
`irzserver4` на `127.0.0.1:3306`, `spawn('java', [...])` для GpioDaemon с VPS-локальным путём к
`Service.jar`. Ни один объём настройки dev-машины это не воспроизведёт без обширного
мокирования — а это отдельная, гораздо более крупная задача, не входящая в P0-10.

**Предложенный механизм:** второй pm2-процесс прямо на VPS, другой порт (например 3006),
отдельная копия `app.db` (через уже готовые и проверенные `backup-db.js`/`restore-db.js` из
P0-05/P0-06), **не подключён к nginx/`askue.o-dir.ru`** — без публичного трафика. Кандидат
деплоится туда первым, проверяется живьём, и только потом — в реальный `irz-web-gpio`/3005.

**Не провижинится в этой задаче.** Настройка означает запись на файловую систему VPS и запуск
нового pm2-процесса — это изменение на стороне VPS, требующее отдельного явного разрешения
владельца, та же граница, что соблюдалась всю Phase 0 (P0-02 не ротировал пароли, P0-05 не
ставил cron). Готово к исполнению сразу после разрешения — точные шаги ниже.

## Точные шаги для запуска Уровня 2 (готовы, не выполнены)

0. **Предпосылка, обнаруженная при проектировании этой процедуры, не решённая заранее:**
   `server.js` жёстко хардкодит `const PORT = 3005;` — без правки на чтение `PORT` из
   переменной окружения (с фолбэком на 3005) второй процесс на другом порту технически
   невозможен. Это маленькая, аддитивная правка кода — **не сделана в рамках P0-10** (вне его
   строгого scope, это не «построить staging-процесс», а «подготовить сам `server.js` к тому,
   чтобы staging-процесс мог существовать») — но обязательна перед первым реальным запуском
   Уровня 2, должна войти в ту же задачу, которая реально проведёт провижининг.
1. На VPS: `mkdir /opt/irz-web-staging`, скопировать `fetched/*` туда (тот же paramiko-паттерн,
   что и для прод-деплоя).
2. Снимок `app.db` в `/opt/irz-web-staging/data/` — через `backup-db.js` (снять с реальной БД)
   → `restore-db.js` (развернуть в staging-путь), тем же механизмом, что уже реализован и
   проверен в P0-05/P0-06.
3. Новый pm2-процесс: `pm2 start /opt/irz-web-staging/server.js --name irz-web-staging`, с
   `PORT=3006` в окружении (см. предпосылку п.0).
4. Проверка живьём — `curl` на `127.0.0.1:3006` прямо с VPS (или через SSH-туннель с dev-машины),
   ручное упражнение изменённой функциональности.
5. Если всё в порядке — тот же код деплоится в реальный `/opt/irz-web/` (уже существующий
   paramiko-паттерн) + `pm2 restart irz-web-gpio`.
6. Staging-процесс можно оставить как постоянный фикстур для следующего раза или снести —
   решение владельца, не техническое ограничение.

## Полный жизненный цикл (оба уровня вместе)

```
git commit (ревьюируемый diff)
      │
      ├── Уровень 1 (для изменений в границах одного модуля) ── уже работает сегодня
      └── Уровень 2 (для изменений, затрагивающих весь HTTP-конвейер) ── ждёт разрешения
      │
владелец проверяет отчёт
      │
отдельное явное разрешение на деплой
      │
paramiko-деплой в /opt/irz-web/ (существующий механизм, не меняется)
      │
node --check на сервере → pm2 restart irz-web-gpio → pm2 logs (несколько минут без ошибок)
```

## Rollback

- **Уровень 1:** нечего откатывать — полностью локально/изолированно, `fetched/` не менялся.
- **Уровень 2:** staging-процесс одноразовый — `pm2 delete irz-web-staging`, на продакшн не
  влияет никак (не подключён к nginx, отдельная копия данных).
- **Сам прод-деплой:** `git revert` + повторный деплой предыдущей версии файла + `pm2 restart` —
  уже существующий паттерн, применяется каждый раз, когда потребуется откат.

## Acceptance criteria этой задачи — что выполнено, что нет

- ✅ Документированная, повторяемая процедура существует (этот файл).
- ✅ Механизм Уровня 1 технически готов и уже подтверждён — не единожды, а 4 раза подряд на
  реальных задачах этой же фазы (таблица выше), каждый раз до стадии verify включительно.
- ⛔ Уровень 2 — механизм спроектирован и задокументирован до последнего шага, но **не
  запущен** — провижининг на VPS требует отдельного явного разрешения владельца, не входит в
  scope P0-10 согласно его собственной карточке.
