# 00 — STAGE 3: IMPLEMENTATION PLAN — OVERVIEW & GOVERNANCE

> **Это только план.** В процессе подготовки этого документа не написано ни строчки кода
> продукта, не изменена ни одна production-система, ни одна БД. Каждая задача ниже исполняется
> отдельно, по явной команде владельца («Execute Task P0-01»), а не автоматически по факту
> существования этого документа.

## Источник

Каждая задача здесь — прямое следствие утверждённых решений `RECONCILIATION/*`
(2026-09-09, см. `RECONCILIATION/00_FINAL_ARCHITECTURE.md` §5 и статусы AUTHORITATIVE в
`RECONCILIATION/05_ARCHITECTURE_DECISIONS.md`). Ничего нового не изобретено — этот документ
разбивает уже утверждённую архитектуру на исполнимые, независимо проверяемые единицы работы.

## Обязательное правило (ADR-18, `RECONCILIATION/05_ARCHITECTURE_DECISIONS.md`)

**Если при исполнении любой задачи обнаруживается конфликт или неоднозначность между
утверждённым (AUTHORITATIVE) решением владельца и фактами `AUDIT/*`/`RECONCILIATION/*`/этим
планом — задача НЕ решает конфликт самостоятельно.** Вместо этого:
1. Работа по конкретному пункту, где обнаружен конфликт, останавливается.
2. Конфликт фиксируется как `OPEN OWNER QUESTION`: где именно, в чём расхождение, какие
   варианты рассматривались.
3. Остальные, не связанные с этим конфликтом задачи можно продолжать.

Это касается и ситуаций «решение не специфицировано достаточно детально для исполнения» —
несколько задач ниже уже отмечены как требующие уточнения владельца перед исполнением (не
после) именно по этой причине, не из экономии слов.

## Статусы закрытия задачи (введено 2026-09-09, прецедент — P0-02)

Задача считается закрытой для целей гейта Phase 0 в одном из трёх статусов — они не
равнозначны, и важно не путать второй с первым:

| Статус | Что значит | Снимает ли гейт для этой задачи |
|---|---|---|
| **DONE** | Acceptance criteria исходной карточки задачи выполнены полностью, как написано | Да |
| **DEFERRED / ACCEPTED OWNER RISK** | Владелец сознательно решил не исполнять задачу (или часть её) сейчас, зная риск, который это оставляет открытым — с явной причиной и обязательством вернуться отдельным окном. Не является техническим провалом или незавершённой работой Claude Code — это решение владельца, не подлежащее самостоятельному пересмотру Claude Code | Да, гейт снимается — задача не блокирует переход к следующим, но **риск остаётся в `RECONCILIATION/04_RISK_REGISTER.md` как открытый**, не как закрытый |
| **BLOCKED / OPEN OWNER QUESTION** | Найден конфликт или недостающая информация (ADR-18), исполнение приостановлено до ответа владельца | **Нет** — эта задача продолжает блокировать гейт, пока вопрос не снят (либо решением, либо явным переводом в DEFERRED тем же способом) |

Разница между DEFERRED и BLOCKED принципиальна: BLOCKED — Claude Code не может продолжать без
ответа владельца (вопрос открыт). DEFERRED — владелец УЖЕ ответил, ответ таков «не сейчас, вот
почему», и это осознанное, окончательное для текущего момента решение, не незакрытый вопрос.

**Как задача переходит в DEFERRED:** только явной командой владельца, зафиксированной текстом
в этом плане и в `RECONCILIATION/04_RISK_REGISTER.md` — не предположением Claude Code о том, что
владелец, наверное, не против подождать.

## Формат задачи

Каждая задача — фиксированный набор полей, чтобы её можно было исполнить изолированно:

| Поле | Смысл |
|---|---|
| **Task ID** | Уникальный идентификатор (`P0-01`, `P1-02`, ...) — то, что называется в команде «Execute Task X» |
| **Phase** | К какой фазе `RECONCILIATION/03_IMPLEMENTATION_SEQUENCE.md` относится |
| **Цель** | Что и зачем меняется, одним-двумя предложениями |
| **Файлы/модули** | Конкретные пути — не «где-то в server.js», а точные файлы/участки |
| **Зависимости** | Какие задачи должны быть закрыты раньше |
| **Разрешено менять** | Явный периметр правки |
| **Запрещено менять** | Явно то, что задача не должна трогать, даже если «заодно удобно» |
| **Acceptance criteria** | Как понять, что задача выполнена корректно |
| **Tests/regression checks** | Что конкретно прогоняется/проверяется |
| **Staging verification** | Как проверяется до продакшена |
| **Production verification** | Как проверяется после деплоя |
| **Rollback plan** | Как откатить, если что-то пошло не так |
| **Risk** | Уровень + конкретная причина, не общие слова |

## Почему Phase 2-7 не расписаны так же детально

Полная детализация каждой задачи для Partner Network/AI Revenue Network/и т.д. сейчас означала
бы либо (а) придумывать технические детали доменов, которые ещё не спроектированы глубже
списка сущностей в `03_TARGET_ARCHITECTURE.md` (нарушение принципа «не выдумывать функции» —
Stage 2.5A дала решения по существующему коду и структурные ADR, но не проектировала, например,
конкретный алгоритм расчёта партнёрской комиссии на уровне SQL-запросов), либо (б) писать
задачи, которые почти наверняка изменятся после того, как Phase 0-3 дадут новую информацию
(например, как выглядит `Organization` в реальном коде повлияет на то, как `partners` на неё
ссылаются). Вместо этого `03_PHASES_2-7_OUTLINE.md` даёт scope и порядок на уровне epic'ов —
детализация каждой фазы в формате этого документа готовится отдельно, когда фаза становится
актуальной (то есть после успешного завершения предыдущей).

## Как использовать этот план

Владелец называет `Task ID` («Execute Task P0-01») → задача исполняется строго в границах,
описанных в её карточке → по завершении отчитывается по acceptance criteria → следующая задача
называется отдельно. План не подразумевает автоматического перехода от одной задачи к другой.
